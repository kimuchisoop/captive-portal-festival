# 導入・更新の入口

アプリ0.10.0 / 文書改訂docs1 / 2026年10月20日

この文書を導入・起動・停止・更新の入口とします。以下のコマンドは将来作業するときの手順です。今回、インストール、起動停止、設定適用、移行、確認コマンド、各種試験は実行していません。

## 作業を選ぶ

| 状況 | 進む先 | 使わない操作 |
|---|---|---|
| 保存先もDBもまだない | 新規導入 | 既存DBへのinit |
| 同じ版で起動・停止する | 日常の起動と停止 | init・upgrade-data |
| 0.7～0.10.0のDB形式4を引き継ぐ | 形式4からのコード更新 | 通常はinit・upgrade-dataとも不要 |
| DB形式2・3を引き継ぐ | 旧形式からの更新 | 通常起動による自動移行 |
| 障害からデータを復元する | 復旧の入口 | 現行DBへの上書き復元 |
| 名前・SSID・会期・窓口だけを変える | 案内情報の変更 | APやスイッチの設定変更 |

版の番号だけで互換性を判断しません。上表の形式4は本プロジェクトの同じスキーマを持つ配布版を対象とし、不明な改変版は担当者が確認します。docs1は文書のみの改訂です。

## 新規導入

対象はCPython 3.12・Windows x64と、専用の空MySQL DBです。同梱wheelはこの環境向けで、Python本体・MySQL本体は含みません。ポータルを動かすサーバーの正式OS・配置先は未確定で、VyOSのcore-rtへこのWindows版を導入する前提にはしません。

展開した`server`フォルダーを作業場所にします。実行環境、接続ファイル、データ保存先は区別します。例示パスは本番の決定値ではありません。既存MySQL80や学校の共有DBへ初期化しません。

1. DB管理者が空の専用DBと専用利用者を用意します。初期化用の権限と通常運用の権限は既存の[運用と復旧](運用と復旧.md)を参照します。
2. 同梱の固定wheelとハッシュを使う導入を標準の入口にします。古いREADMEの通常`pip install -r requirements.txt`の例は使わず、次を使用します。`-Online`を指定しない限りネット接続へフォールバックしません。

```powershell
.\install-dependencies.ps1 -Python 'C:\PathToPython312\python.exe'
```

3. 対話端末でMySQL接続情報を入力し、保護された新規フォルダーへ保存します。パスワードを引数へ書きません。

```powershell
.\.venv\Scripts\python.exe .\manage.py --home 'C:\FestivalWiFi\connection-new' configure-mysql
```

4. 専用空DBを指定して、新規データフォルダーを初期化します。通常の導入では`--sample-policy`を付けません。受付停止・本番無効・自動削除停止のまま始めます。

```powershell
.\.venv\Scripts\python.exe .\manage.py --home 'C:\FestivalWiFi\data-new' init --db-config 'C:\FestivalWiFi\connection-new\mysql.json'
.\.venv\Scripts\python.exe .\manage.py --home 'C:\FestivalWiFi\data-new' add-admin owner --role settings
```

`install.ps1`は依存の導入と初期化をまとめる代替手順です。上記のinitと重ねて実行しません。初期管理者は自動作成されず、パスワードは対話入力です。MFAの登録は[追加機能](追加機能の使い方.md)を参照します。

## 日常の起動と停止

監視役とapp/workerのまとめ起動を標準の運用手順とします。同じOS利用者・同じデータ保存先・同じ展開版で実行します。

```powershell
.\operate.ps1 -DataDirectory 'C:\FestivalWiFi\data-new' -Action start
.\operate.ps1 -DataDirectory 'C:\FestivalWiFi\data-new' -Action status
.\operate.ps1 -DataDirectory 'C:\FestivalWiFi\data-new' -Action stop
```

`operate status`はその監視役の状態です。直接起動したapp/workerが残っていない証明にはなりません。旧版を含め直接起動した場合は、起動した各端末からCtrl+Cで終了し、その保存先・プロセスの停止を担当者が確認します。無関係のPythonやMySQLサービスを一括停止しません。

`start.ps1 -Mode serve`と`-Mode worker`は各端末からの直接起動用として残します。まとめ起動と併用しません。電源断後の自動起動サービス登録はこの手順に含みません。

起動時の成功は機器の通信許可を意味しません。通常の既定URLは`http://127.0.0.1:8890/admin`ですが、実際は保存先の`origin`を使います。開発用プレビューの一時ポートを正式配信先に転記しません。

## 形式4からのコード更新

1. 更新前のコード・保存先・DB形式・起動方法・担当者を記録します。秘密値は引き継ぎ表へ転記しません。
2. docs1を含む新しい配布を別フォルダーへ展開し、その配布内に新しい実行環境を用意します。旧版を上書きしません。
3. 旧版のappとworkerを停止します。監視役による起動なら旧版の`operate stop`、直接起動なら各端末から停止します。
4. 更新前の版に対応する暗号化バックアップ、設定、対応鍵、必要なファイルを保全します。復旧用一式はDB単体バックアップと別です。詳細は[復旧とオフライン導入](復旧とオフライン導入.md)を参照します。
5. 同じDB形式4・同じスキーマなら、既存の保護された保存先を新しい版で使用します。initやupgrade-dataを繰り返す必要はありません。
6. 新版を起動する時期と、起動前チェック・画面確認を再開する時期を担当者が決めます。**現在は試験保留のため、この資料整理では切り替えを実行していません。**

コードだけを戻せる場合と、DB復旧が必要な場合を分けます。更新後の記録を古いバックアップで上書きしません。DB形式が異なる旧コードを現行DBへ直接接続せず、必要なら旧コード・対応バックアップ・別の新しい空DBで復旧します。

## 旧形式からの更新

DB形式2・3だけが`upgrade-data`の対象です。旧プロセスの停止、対応する旧版でのバックアップ、旧コード・鍵の保全、DDL権限の準備後に明示実行します。今回は保留です。

```powershell
.\.venv\Scripts\python.exe .\manage.py --home 'C:\FestivalWiFi\existing-data' upgrade-data
```

MySQLのDDLは途中で確定することがあるため、失敗時のマーカーやログを消して起動しません。詳しくは[運営準備とバックアップ検証](運営準備とバックアップ検証.md)へ進みます。SQLite試作データの自動移行手順ではありません。

## 案内情報の変更

学校祭名・SSID・会期・窓口は管理画面で**変更案**を保存し、停止中にCLIで適用します。保存＝承認・即時適用ではありません。日時の正本は受付日時と共通です。正式会期の確認欄が未チェックなら、来場者へ試験用の日時を表示しません。

詳細は[案内情報と入力保護](案内情報と入力保護.md)を使います。運営責任者の確認前に空欄を推測で埋めません。

## 規約変更

0.10.0では管理画面の下書き保存 → プレビュー → 明示的なローカル適用が入口です。[追加機能の規約説明](追加機能の使い方.md)を参照します。適用履歴がDBにあると、初期ひな形ファイルの編集よりDBの適用版が優先されます。

旧READMEの「termsファイルとIDを書き換えて再起動」だけで適用できると判断しません。正式な規約の承認と、ローカル画面での適用は別です。以前の本文・同意・適用履歴を保持します。

## 復旧の入口

| 保全物 | 含むもの・扱い | 詳細 |
|---|---|---|
| DBバックアップ | MySQLのアプリ用テーブル。設定・MySQLアカウント等の全部ではない | [運用と復旧](運用と復旧.md) |
| 分割バックアップ | 大容量向けの暗号化DBスナップショット。形式に対応した版が必要 | [復旧とオフライン導入](復旧とオフライン導入.md) |
| 復旧用一式 | DBと対象設定・対象ファイル。別置き鍵と専用復元手順を使う | [復旧とオフライン導入](復旧とオフライン導入.md) |

復元は新規フォルダー・別の空DBを対象とします。暗号文だけ・鍵だけで復旧一式が揃ったとは判断せず、対応関係と担当者を記録します。復号・復元の試験は現在保留です。
