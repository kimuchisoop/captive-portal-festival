# 予備サーバーへの移行・復旧手順

0.7.0 / DB形式4 / 本書は作業手順です。予備の実機への移行や学校の切り替えは行っていません。移行先の所有者・OS・DB・保管担当は未確定です。

## 必要な保存物

| 保存物 | 扱い |
|---|---|
| 採用版ZIP・SHA256・requirements | 元版も残す。別の仮想環境へ導入する |
| 新しい暗号化MySQLバックアップ | 23テーブルの同意・監査・規約・通知・引き継ぎ・確認記録を含む |
| 対応するbackup.key | 暗号文とは分けて、承認された暗号化媒体・鍵管理先に保管。チャット・メール・共有ZIPへ入れない |
| 設定と規約・AP情報 | config.json、terms.ja/en.txt、device-profile.json（ある場合）。通常のDBバックアップには含まれない |
| session.key・mfa.key | 元環境の保全用として制限された保管先へ保存。移行後に旧セッションを復活させる目的には使わない |
| ファイルの記録 | runtimeログ、support-reports、configuration-history、過去バックアップ、診断資料等。元を削除せず、承認した暗号化先へ複製 |
| DB接続情報 | 元のmysql.jsonを配布しない。移行先専用DB・利用者で新しく作成 |
| 証明書と秘密鍵 | 配信サーバー側で別管理。期限・SAN・チェーン・アクセス権を確認。新ホストへの無条件な複製はしない |

ログを含む複製には利用者情報や接続情報が含まれる可能性があるため、保管先・担当・アクセス権を決めます。鍵を失うと旧暗号化バックアップは復元できません。サーバーのディスク全体をそのまま公開共有しません。SQLデータディレクトリを稼働中に単純コピーして移行する方法は採りません。

## 切り替え前

1. 責任者・作業担当・確認者・開始時刻・中止条件を記録する。RPO（許容する記録の遅れ）とRTO（復旧までの目標時間）は未承認なので実測して決める。日次バックアップだけなら最大約24時間に加え失敗期間分が失われ得るため、要件と照合する。
2. 新しいZIPのSHA256とverify_package.pyを確認する。予備側へ別の仮想環境を作りrequirements.txtを導入してpip checkを通す。元の実行環境や旧版は保持する。
3. 元のapp/workerを止め、旧版のbackupで最終スナップショットを作成する。取得開始・終了時刻と暗号文SHA256・対応する鍵の管理識別名だけを記録する。鍵自体を記録票へ貼らない。
4. verify-backupで復号を確認する。可能ならverify-restoreで別の空DBへの実復元・内容比較を行う。元のDBへ上書きしない。
5. ファイルのログ・設定履歴・資料を承認された保管先へ複製し、ファイル件数とSHA256を照合する。元ファイル・途中失敗の資料も削除しない。

## 予備側の復元

1. 学校の他システムと区別した新しい空MySQL DBを作る。初期化に必要なDDL/TRIGGER権限と、通常運転のSELECT/INSERT/UPDATE/DELETEを分けて管理する。
2. 保護された新しいフォルダーへconfigure-mysqlで接続設定を作成する。パスワードは対話入力する。別ホストのMySQLには信頼するCAとホスト名の検証が必要。
3. 新しい未作成の復元先を指定してrestore-to-newを実行する。入力には暗号文・対応する旧backup.key・移行先接続ファイルを指定する。
4. prepare-restoredを実行する。新しいconfig/session.key/backup.key/mfa.keyを生成し、受付停止・AP未接続を維持する。旧セッションは復活せず、許可は失効、未完了操作は要照合、既存の追加認証は再登録待ちとなる。
5. 元config.jsonを丸ごと上書きしない。承認されたイベント設定・時刻・保存方針・規約を確認して必要な項目だけ戻す。origin、HTTPSの二つのホスト、プロキシ、容量警告は移行先用に見直す。production_enabled=falseとautomatic_deletion_enabled=falseを維持する。
6. 対話的な管理者認証の再登録・復旧を正規のサーバー端末で行う。旧mfa.keyを置いてneeds_resetを手で解除することはしない。
7. サーバーを起動し、MySQL診断・監査件数・同意件数・規約ハッシュ・通知/当日チェック履歴を照合する。verify-restoreを元環境で使えばスナップショットとの自動比較ができる。時刻・health/jobs・新しいバックアップを確認する。
8. support-reportsの旧ファイルは旧環境/保管先に保持し、必要に応じ資料を新規作成する。過去のバックアップと旧鍵もそのまま保管する。新しいbackup.keyと混同しない。

```powershell
# 新しい接続情報用フォルダーと、新しい復元先は別にする
.\.venv\Scripts\python.exe .\manage.py --home 'C:\FestivalWiFi\recovery-connection-new' configure-mysql
.\.venv\Scripts\python.exe .\manage.py --home 'C:\FestivalWiFi\recovered-data-new' restore-to-new --source 'D:\ApprovedBackup\実在のバックアップ.fernet' --key-file 'E:\ApprovedKeys\対応する旧backup.key' --db-config 'C:\FestivalWiFi\recovery-connection-new\mysql.json'
.\.venv\Scripts\python.exe .\manage.py --home 'C:\FestivalWiFi\recovered-data-new' prepare-restored
```

## 切り替え判断・中止

現状の配布版は本番受付・AP通信許可が未実装のため、復元成功だけで来場者の通信提供開始とは扱いません。将来の切り替えには証明書・DNS・ネットワーク・AP・IPv6・利用期限の実機確認と学校側の承認が必要です。

件数や規約が一致しない、バックアップ認証に失敗、初期化マーカーが残る、権限やTLSを確認できない場合は切り替えを中止します。復元先を削除して使い回さず、新しい空DB・新しいフォルダーで再試行します。元環境は保全します。同時に両サーバーで受付を始めないでください。

切り戻しでは元版と元DBを使います。移行先で追加記録が生じた場合は、機械的に元DBへ戻すと記録が欠落するため、両方を保全して記録の突合・責任者判断を先に行います。形式4のDBを旧形式2/3専用コードへ直接つなぎません。
