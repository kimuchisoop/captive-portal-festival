# 運営準備とバックアップ検証

リリース0.7.0 / MySQL専用 / DB形式4 / ローカル開発版

## バックアップ一覧の検証結果

記録担当・設定管理者が一覧を参照し、「復号を検証」から保存した暗号文を実際に読み取ります。認証付き復号、バックアップ形式、対応するDB形式とスキーマ、行の構造を確認して結果をMySQLへ保存します。失敗も履歴に残し、失敗を確認済みにしません。秘密情報や平文の内容は画面・履歴に表示しません。

復号は、保存したデータを読めることの確認です。別のDBへ復元できたこととは分けて表示します。「検証履歴を表示」は直近100件を表示し、それ以前もDBに保持します。APIでは履歴の続きを取得できます。画面を開くだけでは復号や復元を実行しません。

検証日時・暗号文のSHA256・検証時点のファイル容量と更新日時を保存します。一覧では容量または更新日時が変わると「検証後にファイル変更」と表示します。同じメタデータを意図的に偽装するOS管理者に対する証明ではありません。改めて検証すれば現在の暗号文を読み直します。

画面の検証には現在のデータフォルダーのbackup.keyを使用します。以前の鍵が必要な場合は、保護された端末で鍵ファイルを明示します。鍵の内容を引数へ入力しません。

```powershell
.\.venv\Scripts\python.exe .\manage.py --home 'C:\FestivalWiFi\local-data' verify-backup '実在するbackup-日時-UUID.fernet'

# 必要な場合だけ、対応する旧鍵のファイルを指定
.\.venv\Scripts\python.exe .\manage.py --home 'C:\FestivalWiFi\local-data' verify-backup '実在するbackup-日時-UUID.fernet' --key-file 'E:\ApprovedKeys\旧backup.key'
```

従来の.fernet形式の検証処理の読み取り上限は暗号文256MiBです。新しい.sffbackupの分割処理は[復旧とオフライン導入](復旧とオフライン導入.md)を参照してください。上限を超えた場合は検証失敗として記録し、ファイルを削除しません。バックアップの作成処理の変更ではありません。大きな本番データに対するストリーム形式の検証は、この版には含みません。

## 別の空DBへの復元検証

MySQL管理者が、元のDBと別の**空の専用DB**と、接続ファイルを準備します。復元時には初期化用のDDL・TRIGGER権限も必要です。元のDBや既存システムのDBを指定しないでください。検証先フォルダーは存在しない新しい場所を指定します。

```powershell
.\.venv\Scripts\python.exe .\manage.py --home 'C:\FestivalWiFi\local-data' verify-restore '実在するbackup-日時-UUID.fernet' --destination 'C:\FestivalWiFi\restore-check-新しい名前' --db-config 'C:\FestivalWiFi\restore-connection\mysql.json'
```

処理は、バックアップを復号し、新しい空DBへ復元し、復元先の初期設定を作成します。保存した同意・監査・規約・通知・対応履歴・容量履歴・当日チェック等の内容を元のスナップショットと比較し、旧セッションがなく、許可が失効し、追加認証が再登録待ちであることも確認します。最後に元の暗号文が変わっていないか再確認します。確認が通った場合だけ、元の運営DBへ復元検証の成功を記録します。

復元先の受付は停止したままで、旧端末の通信許可を復活させません。空でないDBは拒否します。失敗した場合も元のバックアップと検証先の資料は削除しません。MySQLのDDLは暗黙コミットを伴うため、不完全なフォルダー・テーブルが残る場合があります。ログを残して原因を確認し、次回は別の新しい空DBとフォルダーを使います。

この処理は実際の復元を行うため、管理画面から任意の接続情報を入力して実行する機能は設けていません。検証先を確認できるサーバー端末で実行します。DB形式2・3の旧バックアップも、対応する旧スキーマで復元してから、その復元先だけを形式4へ更新できます。

## 障害調査資料

運用担当・設定管理者が「障害調査資料を作成」から作成します。調査番号が分かる場合だけ入力し、分からない場合は空欄で作成できます。調査番号はUUID形式だけを受け付け、自由な文章は取り込みません。

資料には、アプリの版、DB形式、ローカル稼働状態、保存件数、定期処理とバックアップからの経過時間、通知の種類・重大度、MySQL接続・TLS・権限の確認結果を含めます。

次の内容は取り込みません。

- 生のログ、同意本文、規約本文、対応メモ、当日チェックの自由記入
- 管理者名、端末識別子、IPアドレス、ホスト名、DB名、接続利用者名
- パスワード、鍵、Cookie、セッション値、MySQLの生の権限文
- 設定ファイル、診断ファイル、任意のパスにあるファイル

必要な値だけを選んで新しい資料を作成し、元のログを削除・改変して資料へ転用しません。作成・ダウンロードを監査に記録します。資料のファイルは保護されたsupport-reportsフォルダーへ保存し、認証された運用担当・設定管理者だけがダウンロードできます。ファイルのSHA256が保存時と異なる場合は配信を拒否します。外部への送信機能はありません。共有前に運営者が内容と共有先を確認してください。

画面には最新20件を表示します。作成済みファイルを自動削除しません。MySQLバックアップには資料の作成履歴とハッシュが含まれますが、support-reportsのファイル自体は含まれません。復元後にファイルがない場合は資料を新しく作成します。旧ファイルの別保管は運営側で管理します。

## 当日の運営チェック

全役割で参照し、運用担当・設定管理者が記録します。確認する日付は日本時間で、開始前・開催中・終了後を選びます。「この日の確認を開始」を押すと、その日・時間帯の共通チェックを開始します。同じ組み合わせを二重に作成しません。

| 時間帯 | 確認内容 |
|---|---|
| 開始前 | MySQL、定期処理、バックアップ、SSID・電波、実端末でのインターネット接続、案内表示、担当者と連絡先の共有 |
| 開催中 | 通知と引き継ぎ、保存容量、エリアの混雑、実端末の接続状況 |
| 終了後 | 提供終了の案内、実機での通信許可終了、最終バックアップ、ログ・記録の保管 |

各項目は未確認から始まり、確認済み・要対応・対象外・未確認として記録できます。未確認以外は担当者を指定し、要対応・対象外には理由が必要です。記録者・担当者・確認日時・内容を保存し、修正も新しい履歴として追加します。別の担当者が先に更新した場合は保存を拒否し、一覧の再確認を求めます。

未確認数・要対応数は画面に表示します。これは担当者が記録する確認表であり、APの実際の接続状態や本番受付を自動的に確認済みにするものではありません。現在のAP未接続という状態は変わりません。連絡先の共有を確認する項目はありますが、この確認表に個人の連絡先を書き込む必要はありません。

## 更新と復旧

DB形式4では4テーブルを追加し、23テーブルとなります。既存の記録・ログは削除しません。通常の起動で自動更新しません。

1. 旧アプリとworkerを停止します。
2. 旧版のbackupコマンドでバックアップを作り、旧コード・対応する鍵・設定を保管します。
3. 新版を別フォルダーへ展開し、依存関係を準備します。
4. DDL権限を用意した上で、保護された同じデータ保存先に対して明示的に更新します。

```powershell
.\.venv\Scripts\python.exe .\manage.py --home 'C:\FestivalWiFi\local-data' upgrade-data
```

5. statusとdiagnose-mysqlを確認し、通常運用の権限へ戻してから起動します。

形式2・3から更新できます。途中失敗した場合はupgrade.incompleteによって起動を拒否します。原因を確認して同じ更新を再実行できます。マーカーやログを手動削除して起動しないでください。旧形式へ戻す場合は旧コードと旧バックアップを使い、別の新しい空DBへ復元します。形式4のDBを旧版のコードへ直接つなぎません。
