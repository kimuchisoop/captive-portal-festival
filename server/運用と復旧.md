# MySQL版 運用・更新・復元

0.7.0 / MySQL DB形式4。ログ・同意記録・通知・バックアップを自動削除しません。

## 開始・停止

1. MySQLの専用DB・利用者・アクセス元を確認する。学校や既存システムのDBを指定しない。
2. statusでMySQL接続とmode=local、production_enabled=falseを確認する。
3. 同じOS利用者・保存先でserveとworkerを起動する。
4. 管理画面でMySQL保存、自動削除停止、最終バックアップと定期処理の日時を確認する。
5. 停止はアプリの両端末でCtrl+C。既存MySQLサービスは停止しない。

## 更新・切り戻し

1. 旧コード、依存版、保護した設定、対応するバックアップと鍵を保管する。ログはそのまま残す。
2. 新版を別フォルダーへ展開し、別の仮想環境に依存関係を導入して試験する。
3. アプリとworkerを停止し、旧版のbackupコマンドで暗号化バックアップを作る。
4. MySQL DB形式を確認する。この版の稼働形式は4だけで、SQLite形式1は受け付けない。既存SQLite試作データの自動移行は行わない。
5. 同じ形式・スキーマであれば旧版へ戻せる。異なる形式の自動移行・自動切り戻しは付属しない。
6. データ復旧が必要なら、対応する旧コードとバックアップを使い、新しい空DBへ復元する。更新後の追加記録が更新前バックアップに含まれないことを記録する。元DB・ログは削除しない。

## バックアップ

```powershell
.\start.ps1 -DataDirectory 'C:\FestivalWiFi\local-data' -Mode backup
```

MySQL内の23テーブルを一貫した読み取りで取得しFernetで暗号化します。同意・監査・通知等を期限で消さずに取得します。バックアップも期限で削除しません。backup.keyと同じDB接続設定はZIPやログへ入れません。鍵の別保管先は運営側で決めてください。

同じディスクだけでは故障に備えられません。別保管先の暗号文と対応鍵を管理者が保管してください。RPO/RTO・保管容量・正式期間は未承認です。

## 復元

別の空MySQL DBとその接続ファイルを用意します。元DBへ上書きしません。初期化に必要なDDL権限は一時的に付与し、完了後は通常権限へ戻してください。

```powershell
.\.venv\Scripts\python.exe manage.py --home 'C:\FestivalWiFi\recovered-data' restore-to-new --source 'D:\ApprovedBackup\実在のバックアップ.fernet' --key-file 'E:\ApprovedKeys\backup.key' --db-config 'C:\FestivalWiFi\recovery-connection\mysql.json'
.\.venv\Scripts\python.exe manage.py --home 'C:\FestivalWiFi\recovered-data' prepare-restored
.\start.ps1 -DataDirectory 'C:\FestivalWiFi\recovered-data' -Mode status
```

復元は暗号文の認証、形式、スキーマのハッシュ、列、MySQL制約を確認します。初期化DDLはMySQLで暗黙コミットされるので、失敗時には空のテーブルが残る場合があります。restore.incompleteがあれば起動せず、ログと元バックアップを残して別の新しい空DBでやり直します。

ログと同意記録を保持し、旧セッション・リンクを復活させません。許可レコードはexpiredまたはrevokedとし、通信許可を再発行しません。prepare-restoredは新しいsession.keyとbackup.key、受付停止の設定を作成します。期限超過記録も削除しません。旧バックアップの鍵と新しいバックアップの鍵を区別してください。

## 通知対応

| 状態 | 対応 |
|---|---|
| 自動削除停止 | 利用者指示による設定。期限は件数確認のみ。ログを削除しない |
| MySQL接続不可 | DBサービス、接続先、利用者権限、TLS、容量を確認。接続パスワードをログへ出さない |
| AP未接続／未完了操作 | この版では実機未接続。受付側の失効を実際の切断完了と扱わない |
| 容量不足 | ログを削除せず、保存容量・保管先を見直す |
| バックアップ失敗・遅延 | 鍵、MySQL権限、容量、workerの稼働を確認。元の鍵やログを削除しない |
| worker停止 | /health/jobsの503と端末を確認。正しい保存先で起動する |

「確認済み」は解決済みではありません。ログアウトや管理者の権限変更では監査記録を保持し、ログイン状態だけを失効します。管理者パスワード変更はサーバー端末でchange-admin --passwordを使います。
