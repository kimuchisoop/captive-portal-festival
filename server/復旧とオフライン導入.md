# 復旧用保存・大容量・オフライン導入・起動前チェック

0.7.0 / MySQL・DB形式4 / 本番受付・AP通信許可は無効を継続します。ログ、旧版、試験DB、途中で失敗した資料を自動削除しません。

## 復旧用の一式保存

通常のDBバックアップに加え、config.json、規約ファイル、session.key/backup.key/mfa.key、AP情報、過去のバックアップ、runtimeのログ、診断資料、support-reports、configuration-historyを暗号化した一式へ保存します。最新のDBスナップショットも含みます。暗号文の内部にファイル一覧と各ファイルのSHA256を保存し、作成後に暗号認証と内容照合を行います。

mysql.json・確認用アカウント・runtimeの制御ファイルは含めません。移行先のDB接続情報は新しく用意します。ソースコード・依存ファイルは別配布のZIPを保管します。保存対象以外の独自フォルダーは一式へ自動追加しないので、導入時に保存物の一覧と照合してください。

アプリとworkerを停止してから実行します。supervisorの状態とロックを照合します。手動で起動したプロセスも止め、DBへの別経路からの書き込みや設定編集を同時に行いません。DBは一貫した読み取り時点の内容であり、作成完了後に追加された記録は含まれません。

```powershell
.\operate.ps1 -DataDirectory 'C:\FestivalWiFi\local-data' -Action stop
.\.venv\Scripts\python.exe .\manage.py --home 'C:\FestivalWiFi\local-data' create-recovery-kit --output 'D:\ApprovedBackup\新しい名前.sffkit' --key-directory 'E:\ApprovedKeys\新しい鍵フォルダー'
```

出力先の親フォルダーは事前に作成し、鍵フォルダーは未作成の新しい場所を指定します。鍵は新しく生成してrecovery.keyへ保存し、暗号文と同じフォルダーやその配下には置けません。実際に別媒体・別障害範囲で保管できるかは担当者が確認してください。この一式は元の暗号鍵も暗号化して含むため、recovery.keyの管理者を限定します。鍵や暗号文を外部へ自動送信しません。鍵の内容をコマンド・ログ・メールへ貼りません。

作成途中は.partialを残し、最後まで認証・内容照合できた場合だけ指定の完成名へ移します。失敗ファイルも削除しません。シンボリックリンクや通常ファイルでないものは拒否します。元の鍵・ログ・バックアップを移動してなくす処理は行いません。

## 復旧用一式からの復元

別の空MySQL DB、その保護された接続JSON、未作成の新しい復元先を用意します。

```powershell
.\.venv\Scripts\python.exe .\manage.py --home 'C:\FestivalWiFi\recovered-new' restore-recovery-kit --source 'D:\ApprovedBackup\実在の一式.sffkit' --key-file 'E:\ApprovedKeys\対応する鍵フォルダー\recovery.key' --db-config 'C:\FestivalWiFi\recovery-connection\mysql.json'
```

暗号認証・全ファイルのハッシュ照合後、保護された別のevidenceフォルダーへファイルを展開します。絶対パス、親への移動、リンク、重複名、余分なデータ、欠落、改変を拒否し、既存ファイルへ上書きしません。DBを新しい空DBへ復元し、同意・監査・規約・通知・対応・確認記録を比較します。受付停止・旧セッション失効・許可失効・追加認証再登録待ちの状態を維持します。

稼働用フォルダーには新しい設定と鍵を生成します。元の設定・鍵・ログ・資料はevidence内にそのまま残し、元configを丸ごと稼働用へ上書きしません。規約・時刻・容量・接続先などを担当者が照合して必要な項目だけ戻します。旧鍵は旧バックアップ用、新鍵は新バックアップ用です。evidenceも秘密情報を含む保管物として扱います。

失敗時は不完全マーカーと途中のフォルダー・DBを保全し、新しい空DB・新しいフォルダーで再試行します。元DBへの上書きや本番の切り替えは行いません。実機の移行判断は[予備サーバーへの移行手順](予備サーバーへの移行手順.md)に従ってください。

## 分割バックアップ

従来の.fernetは暗号文256MiBまでの認証付き検証・復元を継続します。192MiB以上になるとworkerの通知で案内します。上限を超えた従来ファイルをこの版で一括読み込みして復元することはしません。既存の大きな従来ファイルは削除せず、対応する旧環境を保全して個別の変換・復元計画を作ります。

新しい.sffbackupはDBを行単位で取り出し、最大1MiBの平文ブロックごとにFernetで暗号化します。ファイル識別子・連番・終端を認証し、順序変更・別ファイルとの混在・途中欠落・末尾追加を拒否します。復号時も全体をメモリーへ展開せず、各テーブルの件数とハッシュを照合します。DB形式4に対応し、0.6.0以前のコードでは新形式を復元できません。

```powershell
.\.venv\Scripts\python.exe .\manage.py --home 'C:\FestivalWiFi\local-data' backup-stream
# 作成された実在のファイル名を指定
.\.venv\Scripts\python.exe .\manage.py --home 'C:\FestivalWiFi\local-data' verify-backup 'backup-日時-UUID.sffbackup'
.\.venv\Scripts\python.exe .\manage.py --home 'C:\FestivalWiFi\local-data' verify-restore 'backup-日時-UUID.sffbackup' --destination 'C:\FestivalWiFi\stream-restore-new' --db-config 'C:\FestivalWiFi\recovery-connection\mysql.json'
```

定期処理でも使う場合、アプリとworkerの停止・設定保全後にconfig.jsonのbackup_formatをstream-v1へ変更して再起動します。既存設定に項目がない場合と初期設定は、互換性のためfernet-v1を継続します。新規の大容量運用ではstream-v1を選んで検証してください。通常のbackupコマンドは従来形式を作ります。復旧用一式のDBスナップショットは常に分割形式です。

新形式は全体256MiBの制限を持ちませんが、一つのJSON行は4MiBまでです。任意サイズの単一行や無制限の保存量を保証するものではありません。DB、媒体、MySQLのパケット設定と時間、保存先の空きを別途確認します。平文の一時バックアップは作らず、失敗した暗号文も保持します。新形式の作成時もDB監査に記録します。

管理画面からの検証は64MiBまでです。それを超える場合は案内を返し、長時間の検証で運営中のDB書き込みを待たせないよう、サーバー端末のverify-backupを使います。CLIの分割検証は全体をメモリーへ読み込まず、検証後に結果だけを保存します。

## ハッシュ固定・オフライン導入

配布ZIPにはPythonパッケージ12件のwheel、requirements.lock、offline-manifest.jsonが入っています。wheelはPyPIの公開SHA256と照合済みです。ロックには採用したファイルのハッシュを固定し、導入時は全依存に--require-hashesと--only-binaryを適用します。

対象はCPython 3.12・Windows x64です。Python本体、MySQLサーバー、OSのインストーラーは含みません。導入先にPython 3.12の64bit版と、必要なOS環境を事前に準備してください。Linux・ARM・別のPython版に、このwheel一式をそのまま使いません。

```powershell
# コード・wheelを照合し、専用の仮想環境へネット接続なしで導入
.\install-dependencies.ps1 -Python 'C:\PathToPython312\python.exe'
# 初回の空DBと新規データフォルダーを準備済みの場合
.\install.ps1 -Python 'C:\PathToPython312\python.exe' -DataDirectory 'C:\FestivalWiFi\local-data-new' -MySqlConfig 'C:\FestivalWiFi\connection\mysql.json'
```

既定では--no-indexを使い、配布したwheelhouseだけを参照します。ネットへ自動でフォールバックしません。明示した-OnlineではPyPIを使いますが、同じハッシュ固定を維持します。既存の仮想環境・データ・ログを削除しません。別の配布フォルダーへ展開して新しい仮想環境を作る運用を推奨します。SHA256は照合用で、署名や配布者の身元の証明ではありません。

参考：[pipのハッシュ検証とバイナリ限定](https://pip.pypa.io/en/stable/topics/secure-installs/)、[Fernet](https://cryptography.io/en/latest/fernet/)。

## 起動前の一括チェック

```powershell
.\.venv\Scripts\python.exe .\manage.py --home 'C:\FestivalWiFi\local-data' preflight
# DBに接続せずファイル・設定・鍵・権限・依存・配布物を確認
.\.venv\Scripts\python.exe .\manage.py --home 'C:\FestivalWiFi\local-data' preflight --offline
```

不足ファイル、未完了マーカー、受付設定と利用期間、鍵の形式、保存先・秘密ファイルのアクセス権、書き込み可否、依存版、配布物のSHA256、MySQL接続・DB形式・23テーブルをまとめて表示します。秘密値・例外本文・接続パスワードは表示しません。オフライン指定で省略したDB項目を成功扱いにしません。

管理画面の「保守・設定」にも設定管理者だけが実行できる表示を追加しました。サーバー側で権限とCSRFを検査します。チェックは設定を自動変更せず、DBは読み取りのみです。問題があればCLIは終了コード2です。実行時点の確認であり、その後のファイル変更やOS権限変更を保証しません。

serve、worker、supervisorも起動前に設定・鍵・権限・依存・DBを確認し、要修正があれば起動しません。開発用起動では配布ハッシュの検査を省略し、完全な照合はpreflightまたは導入時のverify_packageで実施します。正式な利用条件・AP・公開HTTPSが未確定という注意は、本番準備完了へ読み替えません。
