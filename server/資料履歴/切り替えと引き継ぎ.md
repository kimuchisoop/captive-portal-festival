# 切り替え・障害判断・引き継ぎ

2026年10月20日 / 0.8.0ローカル検証版

本番の通信許可機能は未接続です。この手順で試作の保存・管理機能を切り替えても、学校の来場者をインターネットへ接続する本番サービスは完成しません。

## ローカル版の切り替え

1. 現行版、保存先、MySQLの接続先と形式、運営担当、停止時間を記録する。接続情報や鍵の内容を引き継ぎ表へ転記しない。
2. 0.8.0を新しいフォルダーへ展開し、verify_package.pyで照合する。専用の新しい仮想環境に同梱の固定依存を導入する。旧版を上書きしない。
3. 現行appとworkerを運営手順で停止し、停止状態を確認する。作成日時・検証結果を付けて復旧用一式と別置き鍵を保全する。暗号文と鍵の担当・保管場所を別々に確認する。
4. DB形式4からはスキーマ更新不要。形式2・3からの更新は保存・停止確認後に明示実行する。更新を中断した場合はマーカーを手で消さず、履歴を保全して同じ更新を再実行する。
5. 新版から保存先を指定し起動前チェックを行う。受付停止、production_enabled=false、自動削除停止、AP未接続を確認する。
6. 管理者ログイン、役割、規約、同意記録の閲覧、バックアップ検証、運営通知、ログアウトを確認し、担当者が確認結果を記録する。
7. 記録の書き込みが始まった後は古いバックアップを現行DBへ戻さない。新旧の記録を保全し、新しい空DBへの復元と照合で復旧する。DB形式が変わった場合に旧コードを直接起動しない。

## 障害時の判断

| 状況 | 最初にすること | 復帰の確認 |
|---|---|---|
| 受付・同意保存に失敗 | 受付を止め、運営通知とログを保全。代替の接続案内を掲示 | MySQL接続・起動前チェック・新しい確認記録の保存 |
| 容量警告 | 保存先とDB側の空きを別々に確認。記録は削除せず、担当者が媒体追加や保全先を用意 | 空き容量とバックアップの作成・検証 |
| バックアップ中断 | .partialと鍵を保全。完成品として配布・復元しない | 別名で作成し、復号・復元照合 |
| 復元中断 | 不完全なDBとフォルダーを保全。マーカーを消して起動しない | 別の空DB・新規フォルダーへ復元して照合 |
| 設定更新中断 | 現在設定とconfiguration-history、変更要求の監査を確認 | 有効な設定を確認し、新しい変更案で適用・記録 |
| 証明書・管理接続に異常 | 公開側に管理経路を開放せず、正式証明書・DNS・接続元を確認 | 正しいホストから証明書検証と権限制限を再確認 |
| AP・回線障害 | ネットワーク担当へ、発生時刻・エリア・症状・影響範囲を渡す | 実端末で通信・切断・期限の動作確認 |

## 引き継ぎ記入欄

| 項目 | 記入する内容 |
|---|---|
| 責任者・交代担当 | 氏名、連絡手段、交代時刻 |
| 利用期間 | 正式な開始・終了日時とタイムゾーン |
| 正式な利用案内 | 学校祭名、SSID、提供エリア、言語、窓口 |
| 機器 | APの正式SKU・OS・管理方式、core-routerと各SWの担当 |
| 保存・復旧 | MySQL保存先、暗号文保管先、鍵保管担当、最新検証日時。秘密値は別管理 |
| 未解決通知 | 通知番号、影響範囲、担当、次回確認時刻 |
| 合意する目標 | 許容する記録損失時間、復旧時間、バックアップ間隔 |
| 本番への承認 | 正式規約、ネットワーク担当、保存方針、実機試験の確認者 |

会期、AP仕様、回線容量、同時利用人数、正式保存先は確認待ちです。晴天3,500人・雨天2,400人は一日の来場者計画で、同時接続人数ではありません。担当者や承認済みの目標は未記入のまま確定させないでください。
