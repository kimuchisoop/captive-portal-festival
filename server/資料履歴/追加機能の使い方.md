# 追加機能の使い方

0.7.0 / 2026-10-19 / MySQL・DB形式4 / ローカル専用

## 通知の対応・引き継ぎ

全役割で通知と履歴を参照でき、運用担当・設定管理者が担当者と対応内容を追加できます。担当に指定できるのは有効な運用担当・設定管理者です。自由記入は1,000文字までで、個人情報・パスワード・鍵を書かないでください。

「未着手」「対応中」「対応記録済み」は人の作業状況です。機器や定期処理が検知する「検知中」「検知上は解消」と別々に表示します。対応記録を追加しても監視の検知状態を変更しません。問題が解消後に再発すると発生回を増やし、過去の対応記録を残して新しい対応として扱います。

同じ内容の再送は重複保存しません。別の担当者が先に更新した場合は保存を拒否して一覧の再確認を求めます。一覧の更新時は未保存の入力を置き換えるため、画面に注意を表示しています。自動更新では編集中の入力を置き換えません。一覧は直近の通知100件、過去の引き継ぎ履歴は100件ずつ続きを表示します。

## 規約の下書きとローカル適用

設定管理者が日本語・英語の本文、規約の版、利用方針の版を入力して「新しい下書きを保存」します。本文は各5,000文字、版は各80文字までです。保存のたびに新しい下書きが作られ、以前の下書きは残ります。本文をHTMLとして実行しません。

一覧のプレビューから、保存した日本語・英語を確認します。チェックを入れて「ローカル版に適用」を押すと、このPCの来場者画面で使う版を切り替えます。これは学校の正式承認や公開サイトへの反映ではありません。旧規約・旧同意・適用履歴は保持します。

変更前の画面を開いていた来場者は、旧版の内容のまま新しい同意を作成できません。規約変更の応答を受けた場合は画面を開き直します。適用確認から操作までの間に別の設定管理者が適用した場合も、再確認を求めます。下書き一覧は最新100件です。

適用した版はMySQLに保存され、アプリを再起動しても継続します。初期ひな形のterms.ja.txt等を書き換えても、DBに適用済みの版がある場合はそちらを優先します。以前の適用版へ戻す場合も、その下書きをプレビューして新しい適用履歴として切り替えます。

## 管理者の追加認証

認証アプリを使うTOTP（SHA-1・6桁・30秒）を実装しました。登録は個別の管理者に対してサーバー端末で行い、この配布だけでは誰の追加認証も有効にしません。

```powershell
.\.venv\Scripts\python.exe .\manage.py --home 'C:\FestivalWiFi\local-data' enroll-mfa owner
```

録画・共有されていない対話端末で実行します。表示された登録用秘密情報を認証アプリへ手入力し、アプリのコードで登録を確定します。その後に表示される8個の復旧コードを、このPCとは別の安全な場所へ保管してください。秘密情報と復旧コードは運営ログへ書き出しません。コマンド引数にも入力しません。登録は入力・表示のある対話端末のみ対応です。

登録後はパスワードと追加認証の両方が必要です。追加認証待ちの有効時間は2分、失敗は管理者ごとに15分間で5回までです。パスワードからやり直しても追加認証の失敗回数はリセットしません。時刻ずれは前後1ステップだけを許容し、成功した同じコードは再利用できません。復旧コードも一度だけ使用できます。登録直後のコードは確認時に使用済みになるため、次のコードを待ってログインします。端末の時計を正しく合わせてください。

秘密情報はmfa.keyで暗号化してMySQLへ保存し、復旧コードはハッシュのみ保存します。mfa.keyを他人に渡したり配布ZIPへ含めたりしないでください。再登録すると旧復旧コードは使えなくなり、既存セッションも失効します。過去の使用記録・監査は残ります。

紛失時は未使用の復旧コードでログインします。復旧コードも利用できない場合、サーバーを管理するOS利用者が保護された対話端末で次を実行できます。これはOS管理権限に依存する復旧経路です。

```powershell
.\.venv\Scripts\python.exe .\manage.py --home 'C:\FestivalWiFi\local-data' reset-mfa owner
```

指定した確認文字を入力すると追加認証を解除して監査記録を残し、セッションを失効させます。直後に再登録してください。パスワードの変更だけでは追加認証を解除しません。バックアップからの復元後は、保存済みの追加認証を未確認としてログインを拒否し、端末での再登録を必要とします。旧セッションや追加認証を自動で復活させません。

[TOTPの仕様：RFC 6238](https://www.rfc-editor.org/rfc/rfc6238)

## 起動と停止をまとめる

通常の導入で作成した.venvを使います。Windowsへ常駐サービスや自動起動タスクは登録しません。

```powershell
.\operate.ps1 -DataDirectory 'C:\FestivalWiFi\local-data' -Action start
.\operate.ps1 -DataDirectory 'C:\FestivalWiFi\local-data' -Action status
.\operate.ps1 -DataDirectory 'C:\FestivalWiFi\local-data' -Action stop
```

startはアプリと定期処理を非表示で起動します。監視役は自身が起動した子プロセスだけを扱います。二重起動を防ぎ、終了を検出した子を最大3回再起動します。上限に達したら両方を停止し、runtime配下の記録を残します。起動直後に表示された成功はプロセスの開始を示すため、管理画面で接続・定期処理の最終成功も確認してください。プロセスが動いていても処理が止まる場合は、既存の定期処理停止表示で確認します。

stopはこのデータ保存先に対応する監視役へ停止要求を保存します。MySQL自体や別のPythonプロセスは停止しません。起動・停止・再起動の記録とアプリの出力はruntime配下へ別々の名前で残し、以前のログや停止要求は削除しません。statusは稼働状態・子プロセス・再起動回数を表示します。電源断等で監視役まで終了した場合は自動復帰しないため、状態を確認してstartを再実行します。

環境確認用に-PythonExecutableで既存の仮想環境のpython.exeを指定できます。通常は省略します。設定変更・コード更新前はstopで両方を停止し、更新後にstartしてください。

## 来場者画面の使いやすさ

文字サイズ切り替え、本文へ移動するリンク、規約欄のキーボード操作説明、読み上げ用の状態表示、保存中の表示、保存できない理由を追加しました。同意欄は規約の取得と受付確認ができるまで無効です。言語切り替え時は同意チェックを解除して、選んだ言語の規約を確認し直します。画面上の文字サイズ設定は保存しません。

日本語・英語、狭い画面、キーボード操作を確認します。端末固有のWi-Fi認証画面での動作や、全ての支援技術への適合を保証するものではありません。[W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/)

## 保存容量の増加傾向

定期処理がMySQL推定使用量・バックアップ合計・アプリ保存先の空き容量を1時間に1回記録します。繰り返し画面を開いても同じ時間枠の記録を増やしません。記録は削除せず、画面には直近744点まで表示します。

3点以上かつ24時間以上の実測がある場合だけ、最初と最後の差から日あたりの増加量を計算します。警告値が設定済みで増加が正の場合だけ、その値に達するまでの日数を参考表示します。増加がない場合や警告値未設定の場合は日数を算出しません。MySQLの割当量は段階的に変化するため予測は目安です。別のアプリの書き込みや保存先の変更も考慮した保証値ではありません。MySQL本体のディスク空き容量は引き続き未取得です。

## データ形式と更新

この版はDB形式4・InnoDB23テーブルです。形式2・3から記録を残して更新できます。詳しくは新しい更新手順を参照してください。既存の記録・ログを削除しません。起動時の自動更新は行いません。

1. 旧アプリ・旧workerを停止します。
2. 旧版0.3.0のbackupコマンドでバックアップを作り、旧コードと鍵を保管します。
3. 新版を別フォルダーへ展開し、依存関係を準備します。
4. 保護した同じデータ保存先について、新版で明示的に更新します。

```powershell
.\.venv\Scripts\python.exe .\manage.py --home 'C:\FestivalWiFi\local-data' upgrade-data
```

5. statusとdiagnose-mysqlを確認し、新版で起動します。

MySQLのDDLは暗黙コミットを伴うため、更新失敗時に一部の追加テーブルが残る場合があります。upgrade.incompleteがあれば起動を拒否します。原因を確認した上で同じ更新コマンドを再実行できます。エラー時にマーカーやログを手動削除して起動しないでください。既存の本番DBへの適用は運営側の導入作業です。この開発では専用の試験DBだけで更新を確認しています。

形式2の旧バックアップも、新しい空DBへのrestore-to-newで取り込み、その復元先だけを形式4へ更新できます。形式4のバックアップには新しい6テーブルも含みます。DB内の履歴を含めて復元し、追加認証は再登録待ち、通信許可は無効にします。元のDBへ上書きしません。形式4のDBへ旧版のコードを直接向ける切り戻しはできません。必要なら旧版・旧バックアップを使い、別の新しい空DBへ復元します。

バックアップの復号・復元検証結果、障害調査資料の出力、当日の運営チェックを追加しました。DB形式4への更新が必要です。[運営準備とバックアップ検証](運営準備とバックアップ検証.md)と[HTTPS導入準備](HTTPS導入準備.md)を参照してください。形式2・3のバックアップは別の空DBへの復元に対応します。ログと記録は保持します。
