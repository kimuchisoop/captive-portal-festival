## 1. 現状と制約

- **ローカル確認用です。AP連携（来場者への通信許可）は実装していません。** `adapter=disconnected`、`network_verified=false`、`production_ready=false`は固定です。同意を保存しても「保存済み・通信許可なし」（503 `adapter_unavailable`）になります。
- DBはMySQL 8.0.16以上、DB形式5（31表）。同意・監査・ログ・バックアップ・旧版を**自動削除しません**（決定事項C02）。
- 初期状態は受付停止。`config.json`の`production_readiness`の各値（未承認8項目）を`true`へ書き換えるだけで本番になる機能はありません。
- 配布物はOS署名なし。`SHA256SUMS.txt`で照合します。
- 3,500人/日は来場計画値で、同時接続数ではありません。収容性能は未測定です。

## 3. 導入

### 実行ファイル（推奨）

```text
festival-wifi --version
festival-wifi --self-check
festival-wifi --home <データ保存先> preflight
festival-wifi --home <新規保存先> init --db-config <runtime.json> --maintenance-db-config <maintenance.json>
festival-wifi --home <保存先> add-admin <利用者名> --role settings
festival-wifi --home <保存先> serve      # 別プロセスで worker も起動
festival-wifi --home <保存先> worker
```

- `_internal`フォルダーを実行ファイルの隣に置いたまま使います。配布フォルダーとデータ保存先は分けます。
- 初期管理者は自動作成されず、パスワードは対話入力です。MFAは管理画面で登録します。
- 役割：`settings`（設定管理者）、`operator`（運用担当）、`records`（記録担当）、閲覧のみの役割。

### バイナリの入手・ビルド

| 対象 | 方法 |
|---|---|
| Windows x64 / Linux x86_64 | GitHub Actionsの`build`を手動実行、または`v*`タグ → 下書きReleaseに保存（公開は手動）。非公開リポジトリではActionsの無料枠を消費 |
| FreeBSD 15.1 amd64 | FreeBSD上でビルド（[5章](#5-freebsdへの配置)）。Windows/Linux版はFreeBSDで動きません |
| 手元 | 対象OS上で`python tools/build_binary.py --output <新しい空のフォルダー>`（PyInstaller 6.22.3） |

### ソースから動かす（Windows、オフライン導入）

1. ネットにつながるWindows PCで`tools/fetch-wheelhouse.ps1`を実行 → `server/wheelhouse`にwheel 12個（`requirements.lock`のハッシュと照合済み）。wheelhouseはリポジトリに登録しません。
2. `server`フォルダーごと持ち込み、`.\install-dependencies.ps1 -Python <CPython 3.12のpython.exe>`。最初に`verify_package.py`で`release-manifest.json`と照合します。
3. `.\.venv\Scripts\python.exe manage.py --home <保存先> init ...`以降は実行ファイルと同じサブコマンドです。
4. まとめ起動：`.\operate.ps1 -DataDirectory <保存先> -Action start|status|stop`。直接起動（`start.ps1 -Mode serve|worker`）と併用しません。

### 更新

- 新しい版は別フォルダーへ展開し、旧版を上書きしません。app/workerを停止してからバックアップ・設定・鍵を保全します。
- 同じDB形式5なら既存の保存先をそのまま使います。`init`を繰り返しません。
- DB形式2・3・4からは停止中に明示的な移行が必要です（`upgrade-data`、形式4→5は`workflow_database`の停止中移行）。通常起動による自動移行はしません。失敗時のマーカーやログを消して起動しません。

## 4. DB設定とMySQLの配置

### 接続ファイル

ひな形：`server/runtime.example.json`（サービス用）、`server/db-maintenance.example.json`（保守用）。使える項目は`host`・`port`（数値）・`user`・`password`・`database`・`ssl_ca`だけです。

- 配布フォルダーの外の保護したフォルダーへコピーし、`CHANGE_ME`等を書き換えます。実ファイルをリポジトリに登録しません。
- サービス用と保守用は別アカウントにします（同じだと起動を拒否）。host・port・databaseは両方で一致させます。
- 127.0.0.1/localhost以外では`ssl_ca`が必須で、証明書とホスト名を検証します（無効化する設定はありません）。
- パスワードをコマンド引数に書きません。

### 権限

- DBは空の専用DB。学校や既存システムのDBへ初期化しません。
- サービス用の権限は`server/workflow-privileges.json`の`runtime`の範囲だけ（表ごとのSELECT/INSERT/列単位UPDATE等）。GRANT OPTION・全体権限を付けません。
- `init`後に`festival-wifi --home <保存先> diagnose-mysql`（ソースでは`start.ps1 -Mode diagnose-mysql`）で、接続の暗号化・証明書検証・権限を読み取り確認します。権限を変更しません。

### MySQLの配置（ブランチ）

| ブランチ | 構成 |
|---|---|
| `freebsd/mysql-local` | MySQLを同じFreeBSDマシンに置く（127.0.0.1のみ） |
| `freebsd/mysql-remote` | MySQLを別マシンに置く（TLS＋証明書検証必須） |

このブランチ（`freebsd/mysql-remote`）は**MySQLを別マシンに置く構成**です。FreeBSD側にMySQLを入れないので、ディスクとメモリの負担が最も小さくなります。

```text
[来場者] → [AP/スイッチ/VyOS] → [FreeBSD 15.1：nginx → festival-wifi serve/worker]
                                          │ TLS（CA・ホスト名検証必須）、3306はこの経路だけ
                                          ▼
                                   [DBマシン：MySQL 8.0.16以上]
```

#### DBマシン

1. 学校内用のCAを作り、MySQLサーバー証明書を発行します。証明書のSANに、`host`に書く名前（例：`db.festival.example`）またはIPを必ず入れます。CAの秘密鍵は両マシンに置かず別に保管します。
2. MySQLに`ssl_cert`・`ssl_key`を設定し、`require_secure_transport=ON`にします。
3. 空の専用DB`app_db`、`app_service@<アプリのIP>`、`app_maintenance@<アプリのIP>`を作り、両方に`REQUIRE SSL`を付けます。サービス用の権限は`workflow-privileges.json`の`runtime`の範囲だけにし、`init`後に`diagnose-mysql`で確認します。
4. DBマシンのファイアウォールで、3306をアプリマシンのIPからだけ許可します。

#### アプリ側（FreeBSD）

- `server/runtime.remote.example.json`と`server/db-maintenance.remote.example.json`を`/usr/local/etc/festival-wifi/`へコピーし、festival所有・600にします。
- CA証明書（公開部分のみ）を`/usr/local/etc/festival-wifi/mysql-ca.pem`に置きます。
- pfで、アプリからDBマシンの3306への送信だけを許可します。
- 名前で接続する場合、DNSまたは`/etc/hosts`で名前を固定します（証明書のSANと一致させる）。

#### 注意

- DBとの通信が切れると新規受付は確定しません（現行設計）。復旧後に保存結果を確認します。
- 時刻がずれると証明書検証に失敗するため、両マシンでNTPを有効にします。
- バックアップはFreeBSD側に作られます。DBマシンとも別の媒体・マシンに保管します。

## 5. FreeBSDへの配置

FreeBSD 15.1 amd64。**FreeBSD実機での動作は未確認です。** パッケージ名は`pkg search`で実機の名称を確認してから使います。

### ビルド（配置先とは別のFreeBSD 15.1 amd64で）

配置先にコンパイラやビルド用パッケージを入れないため、ビルド用の環境（別マシン・VM）で行います。

```sh
pkg install python312 py312-cryptography git
python3.12 -m venv --system-site-packages ~/build-venv
~/build-venv/bin/pip install Flask==3.1.3 Werkzeug==3.1.9 waitress==3.0.2 blinker==1.9.0 click==8.5.0 itsdangerous==2.2.0 Jinja2==3.1.6 MarkupSafe==3.0.4 mysql-connector-python==9.7.0 pyinstaller==6.22.3
~/build-venv/bin/python tools/build_binary.py --output /tmp/festival-build
```

- cryptography（とcffi）はPyPIにFreeBSD用wheelがないため、pkgのものを使います。使った版を`pkg info py312-cryptography`で記録します。
- 成功すると`/tmp/festival-build/dist/festival-wifi/`ができ、`--version`・`--self-check`・`--help`まで自動確認します。

### 配置

```sh
pw useradd festival -d /nonexistent -s /usr/sbin/nologin -c "Festival Wi-Fi"
mkdir -p /usr/local/festival-wifi /var/db/festival-wifi /usr/local/etc/festival-wifi
cp -R /tmp/festival-build/dist/festival-wifi/ /usr/local/festival-wifi/
chown -R root:wheel /usr/local/festival-wifi
chown festival:festival /var/db/festival-wifi /usr/local/etc/festival-wifi
chmod 700 /var/db/festival-wifi /usr/local/etc/festival-wifi
```

プログラム（root所有・書込不可）とデータ（festival所有・700）を分けます。DB接続のJSONは`/usr/local/etc/festival-wifi/`に600で置きます。

### 初期化と自動起動

```sh
su -m festival -c '/usr/local/festival-wifi/festival-wifi --home /var/db/festival-wifi preflight'
cp server/deployment/freebsd/rc.d/festival_wifi_* /usr/local/etc/rc.d/ && chmod 555 /usr/local/etc/rc.d/festival_wifi_*
sysrc festival_wifi_serve_enable=YES festival_wifi_worker_enable=YES
service festival_wifi_serve start && service festival_wifi_worker start
```

- rc.dスクリプトは`daemon(8)`で監視・再起動し、`festival`ユーザーで動かします。改行はLF必須（`.gitattributes`で固定）。
- HTTPS配置計画では`deployment_os`に`freebsd`を指定できます。

## 6. 軽量化（容量の少ないマシン向け）

### バイナリ

`tools/build_binary.py`は次を行います。

- 使っていないMySQLのC拡張（`_mysql_connector`・`libmysql`と、それが持ち込むOpenSSL）を入れません。接続は`use_pure=True`のPython実装です。
- 使わない標準ライブラリ（tkinter・unittest・pydoc等）を入れません。
- Windows以外ではデバッグ情報を削除します（`--strip`）。UPX圧縮はウイルス対策ソフトの誤検知を避けるため使いません。

Windowsでの実測：軽量化前52MB → 軽量化後は[13章](#13-試験)の記録を参照。

### OSとデータ

- 配置先にビルド用ツール（コンパイラ、git、pipのキャッシュ）を入れません。`pkg clean -a`でパッケージのキャッシュを消します。
- ZFSならデータ保存先に`compression=lz4`を設定します。
- C02によりログ・バックアップは増え続けます。**バックアップは外部媒体・別マシンへ置き**、古いログは圧縮して別の場所へ移します（削除しない）。`db_warning_bytes`・`backup_warning_bytes`・`min_free_bytes`を実容量から決めます。

### 容量の目安（実測・架空データ）

| 同意件数 | DB推定MiB | 暗号化バックアップMiB | 保存秒 | 復元・照合秒 |
|---|---|---|---|---|
| 1,000 | 4.36 | 1.35 | 0.55 | 4.6 |
| 3,500 | 8.31 | 4.69 | 1.02 | 11.3 |
| 10,000 | 24.30 | 13.39 | 2.20 | 26.2 |

- 晴天3日（1.2端末/人で12,600件）・毎時フルバックアップを全部保存すると、バックアップ合計は約616MiB。6時間ごとなら約110MiB、1日1回なら約34MiB。
- アクセスログは晴天3日で約12MiB（仮定込み）。
- 上はアプリの表だけです。MySQL本体は空でも数百MB使います（[4章](#4-db設定とmysqlの配置)の構成別の設定を参照）。

## 7. 日常運用

1. MySQLの専用DB・利用者・接続元を確認する。
2. `status`でMySQL接続、`mode=local`、`production_enabled=false`を確認する。
3. 同じOS利用者・保存先で`serve`と`worker`を起動する。既定URLは`http://127.0.0.1:8890/admin`（実際は保存先の`origin`）。
4. 管理画面で、MySQL保存、自動削除停止、最終バックアップと定期処理の日時を確認する。
5. 当日の運営チェック（管理画面のチェックリスト）を記録する。

### 通知への対応

| 通知 | 対応 |
|---|---|
| 自動削除停止 | 設定どおり。ログを削除しない |
| MySQL接続不可 | DBサービス、接続先、権限、TLS、容量を確認 |
| AP未接続／未完了操作 | この版は実機未接続。受付側の失効を切断完了と扱わない |
| 容量不足・容量警告 | ログを削除せず、保存容量・保管先を見直す |
| バックアップ失敗・遅延 | 鍵、権限、容量、workerの稼働を確認 |
| worker停止 | `/health/jobs`の503を確認し、正しい保存先で起動 |

「確認済み」は解決済みではありません。管理者パスワードの変更はサーバー端末で`change-admin --password`。

### 案内情報・規約の変更

- 学校祭名・SSID・会期・窓口は、管理画面で変更案を保存 → 別の担当者が確認 → 停止中にCLIで適用（`apply-reviewed-plan`）。保存＝承認・即時適用ではありません。
- 規約は管理画面で下書き → プレビュー → 明示的なローカル適用。DBに適用履歴がある場合はDBが優先です。
- 空欄を推測で埋めません。

## 8. バックアップと復旧

| 保全物 | 内容 |
|---|---|
| DBバックアップ | 形式5（`festival-wifi-stream-backup-v2`、暗号コンテナー`SFFRAME1`）。アプリの31表を一貫した読み取りで取得し暗号化 |
| 復旧用一式 | `festival-recovery-kit-v2`。DBと設定・対象ファイル。鍵は別置き |

- workerが`backup_interval_seconds`（既定86400秒）ごとに作成します。期限で削除しません。
- **同じディスクだけでは故障に備えられません。** 暗号文と鍵を別々の媒体・担当者で保管します。
- 復元は**新しいフォルダー・別の空DB**へ。元DBへ上書きしません。旧セッション・リンクは復活せず、許可は失効扱い、新しい鍵が作られ、受付停止で始まり、MFAは再登録です。手動の解除手順（receipt）まで行ってから起動します。
- 管理画面でバックアップの復号・復元検証を実行し、結果を記録できます（一覧表示だけでは「復元未検査」）。
- 予備サーバーへの切り替え：保存物（バックアップ・鍵・設定・接続情報）を揃え、新しい接続情報用フォルダーと新しい復元先を別にし、作業記録を残します。中止の判断基準も事前に決めます。
- RPO/RTOは未確定。約26秒（1万件の復元）はDB部分だけの値で、サービス全体の復旧時間ではありません。

POSTはOrigin/CSRF必須。画面は英語・日本語・やさしい日本語に対応し、未保存入力の保護、ログイン期限の予告、時間帯別の集計（JST）があります。

## 10. APの確認と連携計画

### 実機で記録する値

`server/device-profile.example.json`を保護したデータフォルダーの`device-profile.json`へコピーし、確認できた値だけ記入します（不明はnull）。`ap-check`／管理画面が未記入の項目を列挙します。

1. 本体ラベルの製品名と製品番号（SKU）。APIN0315はAP-315とIAP-315に共通の認証型式なので、これだけで決めない。
2. 管理画面から起動中のOS名・バージョン、管理先（VC／コントローラー）。
3. コンソールでは**読み取り専用**コマンド（`show version`、Instantなら`show external-captive-portal`）だけ。
4. 初期化・ファームウェア変更・管理方式の変換・設定の上書きはしない。

### 管理方式が判明した後

| 管理方式 | 次に確認する対象 |
|---|---|
| Instant | OS版、VC、外部ポータルの認証方式・HTTPS、RADIUS、端末別の制限 |
| コントローラー | コントローラーの型番とOS、外部ポータル、RADIUS、ロールと端末状態 |

実機で確認が必要な7点：接続元の確認（NAS照合）、HTTPSの認証引き継ぎ先とフォーム項目、RADIUS要求と認証情報の検証、装置による絶対時刻の利用期限、許可ロールと接続状態の観測、対象セッションの切断、IPv6を含む同等の制限。

## 11. HTTPS

- 来場者用と管理用でホスト名を分け、前段のnginx 1つで受けます。管理用は管理ネットワーク（`management_networks`、0.0.0.0/0不可）だけ許可。
- `server/deployment/https-plan.example.json`を記入し、配置計画を検査 → 「停止状態」のnginx設定（アプリへ転送しない）を生成します。証明書ファイルは読みません。
- `deployment_os`は`linux`か`freebsd`。
- 本番導入前に、実証明書・TLS・アクセス制御の試験、AP連携、正式な運用承認が必要です。

## 12. 問い合わせ対応

最初に、場所・時刻・端末の種類・画面の表示・受付番号を聞きます。

| 事例 | 対応の要点 |
|---|---|
| 接続の画面が出ない | SSIDを確認し、ブラウザーで任意のhttpページを開く。正式URLを案内 |
| 同意のボタンが押せない | チェック欄と読み込み状態を確認 |
| 「保存結果を確認できません」 | 成功と扱わず、同じ画面で再確認。受付番号を控える |
| 保存済みだがつながらない | 現在の版はAP連携がないため、通信許可は出ない |
| 「提供期間外」「受付停止」 | 責任者の判断を案内。推測で再開時刻を約束しない |
| 混雑して遅い | 速度や復旧時刻を約束しない。担当へ実測を依頼 |
| 言語・見やすさ・読み上げ | 英語・やさしい日本語、拡大、読み上げ対応 |
| 不審なSSID・QR・証明書警告 | 接続を中止させ、担当へ報告 |

開催前に、窓口・ネットワーク担当・サーバー担当の連絡先を記入しておきます。
