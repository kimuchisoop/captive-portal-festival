## 1. 現状と制約

- **ローカル確認用です。AP連携（来場者への通信許可）は実装していません。** `adapter=disconnected`、`network_verified=false`、`production_ready=false`は固定です。同意を保存しても「保存済み・通信許可なし」（503 `adapter_unavailable`）になります。
- DBはMySQL 8.0.16以上、DB形式5（31表）。同意・監査・ログ・バックアップ・旧版を**自動削除しません**（決定事項C02）。
- 初期状態は受付停止。`config.json`の`production_readiness`の各値（未承認8項目）を`true`へ書き換えるだけで本番になる機能はありません。
- 配布物はOS署名なし。`SHA256SUMS.txt`で照合します。
- 3,500人/日は来場計画値で、同時接続数ではありません。収容性能は未測定です。

| 状況 | 新規受付 | 確認すること |

### 設計案（未承認）

実装済みの2点：設定ファイルを書き換える操作（容量警告値・案内情報・運用方針・移行）は、すべて「アプリとworkerの停止」「同時に1操作だけ」「復元・移行・方針適用の途中で止まっていない」を確認してから書き換えます。CAPPORT（端末への案内）はAPIだけ用意しました（11章）。

| 項目 | 案 | 決まるまで止まる理由 |
|---|---|---|
| 保持記録の取り出し方 | 管理画面の固定CSV出力だけを経路にする。依頼者・目的・範囲を記録し、別の担当者が確認してから出力。出力先は暗号化した媒体で、出力したことは監査に残る。DBからは消さない | 依頼を受け付ける窓口と確認者 |
| 日別の提供時間と再接続 | **提供時間は実装済み**（会期中の毎日、決めた時刻の間だけ新規受付。7章）。残りは再接続：日をまたいだら同意し直す。同じ日の一時的な切断は、利用期限内なら同意の入力をやり直さない | 再接続はAP連携が前提 |
| 削除しない容量運用 | 会期前に見込み量の4倍（既存の暫定案）を確保。警告が出たら、増設か別媒体へのコピーで対応し、アプリは何も消さない。コピー後に元を消すかは責任者が別途判断し、手作業で行う | 保存先担当と別媒体 |
| 来場者セッションの発行上限 | 全体を1分あたり120件から240件へ（開発機の実測、1分あたり348件の約7割。3,000人が一斉に来ても約12.5分）。同じ接続元からの20件とbootstrapは据え置き。FreeBSDの本番機でhttpsで測り直し、実測の7割を上限にする | 本番機での実測と承認 |
| 当日の責任と通知 | 責任者（停止・再開の判断）、サーバー担当、ネットワーク担当、受付窓口を分ける。通知は管理画面だけで外部へ送らない。サーバー担当が1時間ごとに確認し、当日チェックリストに記録する | 担当者の名前と連絡手段 |

## 3. 導入

### 実行ファイル（推奨）

```text
festival-wifi --version
festival-wifi --self-check
festival-wifi --home <データ保存先> preflight
festival-wifi --home <新規保存先> init --db-config <runtime.json> --maintenance-db-config <maintenance.json>
festival-wifi --home <保存先> add-admin <利用者名> --role settings
festival-wifi --home <保存先> serve      # 別プロセスで worker も起動
festival-wifi --home <保存先> worker
```

- `_internal`フォルダーを実行ファイルの隣に置いたまま使います。配布フォルダーとデータ保存先は分けます。
- 初期管理者は自動作成されず、パスワードは対話入力です。MFAは管理画面で登録します。
- 役割：`settings`（設定管理者）、`operator`（運用担当）、`records`（記録担当）、閲覧のみの役割。

### バイナリの入手・ビルド

| 対象 | 方法 |
|---|---|
| Windows x64 / Linux x86_64 | GitHub Actionsの`build`を手動実行、または`v*`タグ → 下書きReleaseに保存（公開は手動）。非公開リポジトリではActionsの無料枠を消費 |
| FreeBSD 15.1 amd64 | FreeBSD上でビルド（[5章](#5-freebsdへの配置)）。Windows/Linux版はFreeBSDで動きません |
| 手元 | 対象OS上で`python tools/build_binary.py --output <新しい空のフォルダー>`（PyInstaller 6.22.3） |

### ソースから動かす（Windows、オフライン導入）

1. ネットにつながるWindows PCで`tools/fetch-wheelhouse.ps1`を実行 → `server/wheelhouse`にwheel 12個（`requirements.lock`のハッシュと照合済み）。wheelhouseはリポジトリに登録しません。
2. `server`フォルダーごと持ち込み、`.\install-dependencies.ps1 -Python <CPython 3.12のpython.exe>`。最初に`verify_package.py`で`release-manifest.json`と照合します。
3. `.\.venv\Scripts\python.exe manage.py --home <保存先> init ...`以降は実行ファイルと同じサブコマンドです。
4. まとめ起動：`.\operate.ps1 -DataDirectory <保存先> -Action start|status|stop`。直接起動（`start.ps1 -Mode serve|worker`）と併用しません。

### 更新

- 新しい版は別フォルダーへ展開し、旧版を上書きしません。app/workerを停止してからバックアップ・設定・鍵を保全します。
- 同じDB形式5なら既存の保存先をそのまま使います。`init`を繰り返しません。
- 対応するDB形式は5だけです。形式2〜4からの移行機能と旧形式のバックアップ（`.fernet`、`festival-wifi-stream-backup-v1`）の読み込みは削除しました（本番運用の前で、旧形式のデータがないため）。

## 4. DB設定とMySQLの配置

### 接続ファイル

ひな形：`server/runtime.example.json`（サービス用）、`server/db-maintenance.example.json`（保守用）。使える項目は`host`・`port`（数値）・`user`・`password`・`database`・`ssl_ca`だけです。

- 配布フォルダーの外の保護したフォルダーへコピーし、`CHANGE_ME`等を書き換えます。実ファイルをリポジトリに登録しません。
- サービス用と保守用は別アカウントにします（同じだと起動を拒否）。host・port・databaseは両方で一致させます。
- 127.0.0.1/localhost以外では`ssl_ca`が必須で、証明書とホスト名を検証します（無効化する設定はありません）。
- パスワードをコマンド引数に書きません。

### 権限

- DBは空の専用DB。学校や既存システムのDBへ初期化しません。
- 権限のSQLは`tools/mysql_grants.py`で`server/workflow-privileges.json`から生成します（表示するだけで実行しません。パスワードは扱いません）。

手順（MySQLの管理者が実行）：

```text
1. CREATE DATABASE app_db CHARACTER SET utf8mb4 COLLATE utf8mb4_bin;
   CREATE USER 'app_service'@'<アプリの接続元>' IDENTIFIED BY '<パスワード>';
   CREATE USER 'app_maintenance'@'<アプリの接続元>' IDENTIFIED BY '<パスワード>';
2. python tools/mysql_grants.py maintenance --database app_db --user app_maintenance --host <アプリの接続元>
   → 表示されたGRANT文を実行
3. festival-wifi --home <保存先> init --db-config <runtime.json> --maintenance-db-config <maintenance.json>
4. python tools/mysql_grants.py runtime --database app_db --user app_service --host <アプリの接続元>
   → 表示されたGRANT文を実行（列単位の権限なので、3で表ができた後に行う）
5. festival-wifi --home <保存先> diagnose-mysql で「専用利用者の権限」がpassになることを確認
```

- サービス用は表・列単位の最小権限だけ。DB全体（`app_db.*`）への権限やGRANT OPTIONを付けると、診断で「要確認」になります。
- 保守用は31表へのSELECT・INSERT・CREATE・ALTER・INDEX・TRIGGER・REFERENCESと、5表（meta・grants・operations・mfa_settings・consent_archive_exports）へのUPDATE。初期化・復元・移行で使います。
- **binlogが有効なMySQL（MySQL 8の初期状態）では、表と一緒に作るトリガーが拒否されます。** MySQL側で`SET PERSIST log_bin_trust_function_creators=ON`にするか、binlogを止めます（同一マシン構成の設定例はbinlogを止めています）。
- `init`は、フォルダーも表も作る前に次を読み取り確認し、足りなければ何をすればよいかを1行で示して止まります：データフォルダーが新しいこと、DBにアプリの表がないこと、保守用権限の過不足、binlogとトリガーの許可。
- 保守用アカウントは表単位の権限なので、アプリと関係ない表がDBにあっても見えません。「空のDB」は、DB管理者が`python tools/mysql_grants.py check --database app_db --user app_service --host <接続元> --maintenance-user app_maintenance`で出る確認用SQL（表の一覧と両アカウントの権限）を管理者アカウントで実行して確かめます。
- 表を作る途中で失敗した場合（MySQLは表を作るたびに確定するため、作った表が残ります）、データフォルダーに`initialization.failed.json`（原因・作られた表・次の手順）を残して止まります。自動では何も削除しません。後始末：原因を直す → DB管理者が空のDBを作り直す（失敗した回の表は空です）→ データフォルダーの名前を変えて退避 → 新しいフォルダーで`init`をやり直す。
- 試験（`tests/test_mysql_grants.py`）で、生成した権限だけで初期化・診断・起動ができることを確認済みです。全試験も、この最小権限のサービス用アカウントで動かして確認済みです。形式4→5の移行（`workflow_database`）も、生成した保守用権限だけで実行でき、移行後に診断・起動できることを確認済みです。

### MySQLの配置（ブランチ）

| ブランチ | 構成 |
|---|---|
| `freebsd/mysql-local` | 主構成。MySQLを同じFreeBSDマシンに置く（127.0.0.1のみ） |
| `freebsd/mysql-remote` | 保険。MySQLを別マシンに置く（TLS＋証明書検証必須） |

**主構成は同一マシンです（C07）。** 別マシンの構成（`freebsd/mysql-remote`）は、組み込みだけで対応しきれなかった場合の保険として保存し、通常は使いません。

```text
[来場者] → [AP/スイッチ/VyOS] → [FreeBSD 15.1：nginx → festival-wifi serve/worker]
                                          │ TLS（CA・ホスト名検証必須）、3306はこの経路だけ
                                          ▼
                                   [DBマシン：MySQL 8.0.16以上]
```

#### DBマシン

1. 学校内用のCAを作り、MySQLサーバー証明書を発行します。証明書のSANに、`host`に書く名前（例：`db.festival.example`）またはIPを必ず入れます。CAの秘密鍵は両マシンに置かず別に保管します。
2. MySQLに`ssl_cert`・`ssl_key`を設定し、`require_secure_transport=ON`にします。
3. 空の専用DB`app_db`、`app_service@<アプリのIP>`、`app_maintenance@<アプリのIP>`を作り、両方に`REQUIRE SSL`を付けます。サービス用の権限は`workflow-privileges.json`の`runtime`の範囲だけにし、`init`後に`diagnose-mysql`で確認します。
4. DBマシンのファイアウォールで、3306をアプリマシンのIPからだけ許可します。

#### アプリ側（FreeBSD）

- `server/runtime.remote.example.json`と`server/db-maintenance.remote.example.json`を`/usr/local/etc/festival-wifi/`へコピーし、festival所有・600にします。
- CA証明書（公開部分のみ）を`/usr/local/etc/festival-wifi/mysql-ca.pem`に置きます。
- pfで、アプリからDBマシンの3306への送信だけを許可します。
- 名前で接続する場合、DNSまたは`/etc/hosts`で名前を固定します（証明書のSANと一致させる）。

#### 注意

- DBとの通信が切れると新規受付は確定しません（現行設計）。復旧後に保存結果を確認します。
- 時刻がずれると証明書検証に失敗するため、両マシンでNTPを有効にします。
- バックアップはFreeBSD側に作られます。DBマシンとも別の媒体・マシンに保管します。

## 5. FreeBSDへの配置

FreeBSD 15.1 amd64。**FreeBSD実機での動作は未確認です。** パッケージ名は`pkg search`で実機の名称を確認してから使います。

### ビルド（配置先とは別のFreeBSD 15.1 amd64で）

配置先にコンパイラやビルド用パッケージを入れないため、ビルド用の環境（別マシン・VM）で行います。

```sh
pkg install python312 py312-cryptography git
python3.12 -m venv --system-site-packages ~/build-venv
~/build-venv/bin/pip install Flask==3.1.3 Werkzeug==3.1.9 waitress==3.0.2 blinker==1.9.0 click==8.5.0 itsdangerous==2.2.0 Jinja2==3.1.6 MarkupSafe==3.0.4 mysql-connector-python==9.7.0 pyinstaller==6.22.3
~/build-venv/bin/python tools/build_binary.py --output /tmp/festival-build
```

- cryptography（とcffi）はPyPIにFreeBSD用wheelがないため、pkgのものを使います。使った版を`pkg info py312-cryptography`で記録します。
- 成功すると`/tmp/festival-build/dist/festival-wifi/`ができ、`--version`・`--self-check`・`--help`まで自動確認します。

### 配置

```sh
pw useradd festival -d /nonexistent -s /usr/sbin/nologin -c "Festival Wi-Fi"
mkdir -p /usr/local/festival-wifi /var/db/festival-wifi /usr/local/etc/festival-wifi
cp -R /tmp/festival-build/dist/festival-wifi/ /usr/local/festival-wifi/
chown -R root:wheel /usr/local/festival-wifi
chown festival:festival /var/db/festival-wifi /usr/local/etc/festival-wifi
chmod 700 /var/db/festival-wifi /usr/local/etc/festival-wifi
```

プログラム（root所有・書込不可）とデータ（festival所有・700）を分けます。DB接続のJSONは`/usr/local/etc/festival-wifi/`に600で置きます。

### 初期化と自動起動

```sh
su -m festival -c '/usr/local/festival-wifi/festival-wifi --home /var/db/festival-wifi set-daily-hours --open 10:00 --close 17:00'
su -m festival -c '/usr/local/festival-wifi/festival-wifi --home /var/db/festival-wifi preflight'
cp server/deployment/freebsd/rc.d/festival_wifi_* /usr/local/etc/rc.d/ && chmod 555 /usr/local/etc/rc.d/festival_wifi_*
sysrc festival_wifi_serve_enable=YES festival_wifi_worker_enable=YES
service festival_wifi_serve start && service festival_wifi_worker start
```

- 毎日の提供時間（`set-daily-hours`）は、サービスを起動する前（止めている間）に設定します。会期中の毎日10:00〜17:00（予定）の例です。詳しくは7章。
- rc.dスクリプトは`daemon(8)`で監視・再起動し、`festival`ユーザーで動かします。改行はLF必須（`.gitattributes`で固定）。
- HTTPS配置計画では`deployment_os`に`freebsd`を指定できます。

### ファイアウォール（ひな形のみ・未導入）

配置先にファイアウォールが入っていない可能性があるため、pfのひな形`server/deployment/freebsd/pf.conf.template`だけ用意しています。導入は担当者が実機で行い、ツールは何も書き換えません。

- 前提：アプリは127.0.0.1だけで待ち受け、外から受けるのはnginxの80/443とSSH（22）だけ。受信は既定で拒否、送信は許可（DNS・NTP・別マシンのMySQLを含む）。
- `CHANGE_ME_IF`（`ifconfig`で確認）、`CHANGE_ME_MGMT_NET`（管理ネットワーク、0.0.0.0/0不可）、`CHANGE_ME_GUEST_NET`（来場者ネットワーク）を実際の値に置き換えます。
- SSHで作業中に締め出されないよう、読み込む前に戻し方を用意します。

```sh
cp server/deployment/freebsd/pf.conf.template /etc/pf.conf   # 値を記入してから
pfctl -nf /etc/pf.conf                                       # 構文確認のみ
kldload -n pf                                                # pfを読み込む（読み込み済みなら何もしない）
echo 'pfctl -d' | at now + 5 minutes                          # 締め出し対策（atrunは5分ごとなので最大10分ほど）
pfctl -e -f /etc/pf.conf
# 別のSSH接続で入れることを確認したら：atq で番号を見て atrm <番号>
sysrc pf_enable=YES pf_rules=/etc/pf.conf
```

- 確認：`pfctl -sr`（読み込まれたルール）、`pfctl -si`（状態）。来場者ネットワークから`https://<来場者用ホスト名>/`、管理ネットワークからSSHと管理画面に届くこと。
- FreeBSD実機では未確認です。

## 6. 軽量化（容量の少ないマシン向け）

### バイナリ

`tools/build_binary.py`は次を行います。

- 使っていないMySQLのC拡張（`_mysql_connector`・`libmysql`と、それが持ち込むOpenSSL）を入れません。接続は`use_pure=True`のPython実装です。
- 使わない標準ライブラリ（tkinter・unittest・pydoc等）を入れません。
- Windows以外ではデバッグ情報を削除します（`--strip`）。UPX圧縮はウイルス対策ソフトの誤検知を避けるため使いません。

Windowsでの実測：軽量化前52MB → **軽量化後36MB**。FreeBSDでは`--strip`も効くため、さらに小さくなる見込みです（未測定）。

### OSとデータ

- 配置先にビルド用ツール（コンパイラ、git、pipのキャッシュ）を入れません。`pkg clean -a`でパッケージのキャッシュを消します。
- ZFSならデータ保存先に`compression=lz4`を設定します。
- C02によりログ・バックアップは増え続けます。**バックアップは外部媒体・別マシンへ置き**、古いログは圧縮して別の場所へ移します（削除しない）。`db_warning_bytes`・`backup_warning_bytes`・`min_free_bytes`を実容量から決めます。

### 容量の目安（実測・架空データ）

| 同意件数 | DB推定MiB | 暗号化バックアップMiB | 保存秒 | 復元・照合秒 |
|---|---|---|---|---|
| 1,000 | 4.36 | 1.35 | 0.55 | 4.6 |
| 3,500 | 8.31 | 4.69 | 1.02 | 11.3 |
| 10,000 | 24.30 | 13.39 | 2.20 | 26.2 |

- 晴天3日（1.2端末/人で12,600件）・毎時フルバックアップを全部保存すると、バックアップ合計は約616MiB。6時間ごとなら約110MiB、1日1回なら約34MiB。
- アクセスログは晴天3日で約12MiB（仮定込み）。
- 上はアプリの表だけです。MySQL本体は空でも数百MB使います（[4章](#4-db設定とmysqlの配置)の構成別の設定を参照）。

## 7. 日常運用

1. MySQLの専用DB・利用者・接続元を確認する。
2. `status`でMySQL接続、`mode=local`、`production_enabled=false`を確認する。
3. 同じOS利用者・保存先で`serve`と`worker`を起動する。既定URLは`http://127.0.0.1:8890/admin`（実際は保存先の`origin`）。
4. 管理画面で、MySQL保存、自動削除停止、最終バックアップと定期処理の日時を確認する。
5. 当日の運営チェック（管理画面のチェックリスト）を記録する。

### 通知への対応

| 通知 | 対応 |
|---|---|
| 自動削除停止 | 設定どおり。ログを削除しない |
| MySQL接続不可 | DBサービス、接続先、権限、TLS、容量を確認 |
| AP未接続／未完了操作 | この版は実機未接続。受付側の失効を切断完了と扱わない |
| 容量不足・容量警告 | ログを削除せず、保存容量・保管先を見直す |
| バックアップ失敗・遅延 | 鍵、権限、容量、workerの稼働を確認 |
| worker停止 | `/health/jobs`の503を確認し、正しい保存先で起動 |

「確認済み」は解決済みではありません。管理者パスワードの変更はサーバー端末で`change-admin --password`。

### 案内情報・規約の変更

- 学校祭名・SSID・会期・窓口は、管理画面で変更案を保存 → 別の担当者が確認 → 停止中にCLIで適用（`apply-reviewed-plan`）。保存＝承認・即時適用ではありません。
- 規約は管理画面で下書き → プレビュー → 明示的なローカル適用。DBに適用履歴がある場合はDBが優先です。
- 空欄を推測で埋めません。

### 毎日の提供時間

会期（`service_start_utc`〜`service_end_utc`）の中で、毎日決めた時刻の間だけ新規受付をします。時間外は「提供期間外」（410 `service_closed`）で、来場者画面の提供日時の欄に時刻も表示されます。アプリとworkerを止めてから設定します。

```text
festival-wifi --home <保存先> set-daily-hours --open 10:00 --close 17:00   # 日本時間（既定）
festival-wifi --home <保存先> set-daily-hours --clear                      # 毎日の制限をなくす（会期の制限は残る）
```

- 変更前後の設定は`configuration-history`に、操作は監査に残ります。日をまたぐ時間帯（例：22:00〜翌2:00）は設定できません。
- 未設定（新規導入の状態）では、会期中は終日受付けます。
- 時間外にしても、すでに保存した同意や、来場者の通信はこの設定では止まりません（AP連携は未実装）。

## 8. バックアップと復旧

| 保全物 | 内容 |
|---|---|
| DBバックアップ | 形式5（`festival-wifi-stream-backup-v2`、暗号コンテナー`SFFRAME1`）。アプリの31表を一貫した読み取りで取得し暗号化 |
| 復旧用一式 | `festival-recovery-kit-v2`。DBと設定・対象ファイル。鍵は別置き |

- workerが`backup_interval_seconds`（既定86400秒）ごとに作成します。期限で削除しません。
- **新規導入の直後は`backup_retention_days`が未設定で、バックアップは作られません。** `preflight`（管理画面の起動前チェックも同じ）が「バックアップの保存方針」を警告します。保存期間を決めて設定してください。
- **同じディスクだけでは故障に備えられません。** 暗号文と鍵を別々の媒体・担当者で保管します。
- 復元は**新しいフォルダー・別の空DB**へ。元DBへ上書きしません。旧セッション・リンクは復活せず、許可は失効扱い、新しい鍵が作られ、受付停止で始まり、MFAは再登録です。手動の解除手順（`release-schema5-recovery`）まで行ってから起動します。解除済みのフォルダーで再実行すると「解除済み」（`already_released`）と返ります。
- 管理画面または`verify-backup`でバックアップの復号検証を実行し、結果を記録できます。復元の確認は`restore-schema5`で新しいフォルダー・空DBへ実際に復元して行います。
- 予備サーバーへの切り替え：保存物（バックアップ・鍵・設定・接続情報）を揃え、新しい接続情報用フォルダーと新しい復元先を別にし、作業記録を残します。中止の判断基準も事前に決めます。
- RPO/RTOは未確定。約26秒（1万件の復元）はDB部分だけの値で、サービス全体の復旧時間ではありません。

### 実機で記録する値

この版はAP連携がないため、会期中に来場者の通信を「同意した人だけ許可する」用途には使えません。会期に間に合う現実的な案は次のとおりです。どれもAP側の機能はAPの型番・OSで変わるため、実機で確認してから決めます。

| 案 | 内容 | このアプリの役割 | 注意 |
|---|---|---|---|

## 11. HTTPS

- 来場者用と管理用でホスト名を分け、前段のnginx 1つで受けます。管理用は管理ネットワーク（`management_networks`、0.0.0.0/0不可）だけ許可。
- `server/deployment/https-plan.example.json`を記入し、配置計画を検査 → 「停止状態」のnginx設定（アプリへ転送しない）を生成します。証明書ファイルは読みません。
- `deployment_os`は`linux`か`freebsd`。
- **CAPPORT（RFC 8908）**：`GET /capport/api`が`application/captive+json`で`{"captive": true, "user-portal-url": "<来場者用オリジン>/"}`を返します。AP連携がないため、常に`captive: true`です。端末へこのURL（来場者用ホスト名のHTTPS）を知らせるのはネットワーク側の設定（DHCPv4オプション114、DHCPv6オプション103、RAオプション37。RFC 8910）で、まだ設定していません。生成するnginx設定は「停止状態」のため、このAPIへも転送しません。
- 本番導入前に、実証明書・TLS・アクセス制御の試験、AP連携、正式な運用承認が必要です。

## 12. 問い合わせ対応

最初に、場所・時刻・端末の種類・画面の表示・受付番号を聞きます。

| 事例 | 対応の要点 |
|---|---|
| 接続の画面が出ない | SSIDを確認し、ブラウザーで任意のhttpページを開く。正式URLを案内 |
| 同意のボタンが押せない | チェック欄と読み込み状態を確認 |

| 「提供期間外」「受付停止」 | 責任者の判断を案内。推測で再開時刻を約束しない |
| 混雑して遅い | 速度や復旧時刻を約束しない。担当へ実測を依頼 |
| 言語・見やすさ・読み上げ | 英語・やさしい日本語、拡大、読み上げ対応 |

開催前に、窓口・ネットワーク担当・サーバー担当の連絡先を記入しておきます。

- 試験をすべて最小権限のサービス用アカウントで動かすようにしました。アプリ側の権限不足は見つからず、古い前提（全権限のアカウント）で書かれていた試験3件を更新しました。

### 実行方法

```text
cd server
python -m unittest discover -s tests -p test_workflow_contract.py -v   # DB不要
node tests/operator_ui.test.cjs

```

MySQL試験は、試験専用のMySQLを用意し、`WIFI_TEST_MYSQL_CONFIG`に次の設定ファイルを指定します。本番と別のMySQL・資格情報を使います。全件で10分以上かかります。試験データとログは自動削除しません。

```json
{"test_only": true, "host": "127.0.0.1", "port": 13308, "user": "root", "password": "<試験用>",
 "maintenance_user": "test_maint", "maintenance_password": "<試験用>", "datadir": "/var/lib/mysql/"}
```

- `maintenance_user`はサービス用と別のアカウント（DB作成・DDLができる試験用）。
- `datadir`は、そのMySQLの`SELECT @@datadir`と一致させます（既存のMySQLを誤って使わないための確認）。省略すると、設定ファイルと同じ場所の`data`フォルダーと照合します。
- Dockerの例：`docker run -d --name festival-wifi-test-mysql -p 127.0.0.1:13308:3306 -e MYSQL_ROOT_PASSWORD=<試験用> mysql:8.4`

試験の初期化は`mysql_fixture.init_home()`を使います。本番と同じ手順で、保守アカウントで`init`し、その後サービス用に生成した最小権限だけを付けた試験用アカウントで起動します（アカウントの接続元は設定の`service_host`、省略時は`%`）。

### 2026-10-30の負荷試験（手元の機械、目安）

`tests/load_check.py`で、来場者1人分の流れ（案内の取得 → セッション開始 → 受付リンクの確認 → 規約の取得 → 同意の保存）を同時に流しました。Windowsの開発用PC、Docker上のMySQL 8.4、サーバーは本番と同じ起動方法（waitress、4スレッド）です。セッション発行の上限（下記）は、この試験のサーバーの中だけで外しています。受付リンクはAP連携の代わりにDBへ直接作っています。

| 条件 | 所要時間 | 同意の保存 | エラー | 1段階の応答（中央値／95%） |
|---|---|---|---|---|
| 60人・同時8 | 22秒 | 1分あたり約160件 | なし | 0.2〜0.8秒／最大1.1秒 |
| 600人・同時32 | 213秒 | 1分あたり約170件 | なし | 1.4〜2.9秒／最大4.1秒 |

読み取り方：

- 同時に増やしても処理件数は1分あたり約170件で頭打ちで、待ち時間だけが延びます。来場者1人の操作（5段階）は、混雑時に合計10秒以上かかります。
- 3,000人が開始と同時に来ると、処理能力だけで約18分かかります。
- **実際には、セッション発行の上限（`session_guard.py`、承認前の暫定値）が先に効きます。** 新しいセッションは全体で1分あたり120件、同じ接続元から1分あたり20件まで。3,000人なら最短25分です。来場者のアドレスがルーターでまとめて変換（NAT）されてサーバーに届くと、全員が同じ接続元になり1分あたり20件になります。
- 遅い主な原因は、DB処理のたびにMySQLへ接続し直していること（毎回TLSを確立）と、書き込みを全体で1件ずつ処理していること（`GET_LOCK`、待ちの上限10秒）です。接続の使い回しは同日に実装しました（下の「改善の試み」）。
- 本番機（FreeBSD）・本番のMySQL配置・実際の無線環境では値が変わります。

改善の試み（同日）：

| 変更 | 600人・同時32の結果 |
|---|---|
| サーバーのスレッド数（設定`server_threads`、既定4）を4・8・16で比較 | 1分あたり160・172・150件。**増やしても改善しない** |
| 来場者向け案内（`/v1/public`）の規約を5秒だけ共有（公開した直後は捨てる） | 案内の取得の中央値が約1.4秒→約0.8〜1.1秒。全体の処理件数は変わらない |
| **MySQL接続の使い回し**（下記）、スレッド4・8・16 | **1分あたり263・348・324件**、エラーなし。8スレッドで各段階の中央値0.7〜1.2秒・95%値1.9秒以内 |

- MySQLへの接続1回は約42ミリ秒（暗号化の確立を含む）、開いた接続での問い合わせ1回は約1.2ミリ秒。接続の処理はPythonで動くため、スレッドを増やしても並行して進みません。処理件数の上限はこの接続の繰り返しで決まっていたため、接続を使い回すようにしました。
- **接続の使い回し**（`database.py`）：終わった取引の接続を、MySQL側で状態（セッション変数・ロック・一時表）を消してから、文字コードと自動確定の設定をし直して次に使います。エラーが起きた接続、状態を消せなかった接続、5分を超えた接続は使わずに閉じます。使う前に接続が生きているか確かめます。待機させる接続は接続先ごとに最大8本、全体で最大16本（超えたら、最も長く使われていない接続先の分から閉じます。使わなくなった接続先の接続が残り続けて、MySQLの同時接続数の上限に達するのを防ぎます）。試験は`tests/test_database_pool.py`。
- 改善後は8スレッドが最も良かったため、`server_threads`の既定を8にしました。
- 3,000人が開始と同時に来ても、処理能力では約9分（改善前は約18分）。ただしセッション発行の上限（1分あたり120件）の方が先に効くことは変わりません。
- アカウントの削除やパスワード変更は、使い回し中の接続には最大5分遅れて効きます（表・列単位の権限の取り消しはすぐ効きます）。
