# キャプティブポータル作成手順書（VyOS連携）

学校祭ゲストWi-Fiで「QRでWi-Fiにつなぐ → 同意画面 → 同意したらインターネットにつながる」仕組みを作り、試すための手順書です。「§3」はこの手順書の「3.」の節を指します。アプリ全体の資料は[ガイド](ガイド.md)を参照してください。

2026-10-30作成の大枠です。**各段階は「作る → 試す → 結果を書く」の順で進め、試験に通ってから次へ進みます。** 値が「要確認」の箇所は、core-rtの実際の設定を見てから確定します。Wi-Fiのパスワード・APIキー・管理者パスワードはこの資料に書きません。

## 0. 目指す仕組み

```text
来場者 ──QRでWi-Fi接続(WPA3)──▶ AP ──▶ core-rt(VyOS) ──▶ インターネット
                                          │ 同意前：DNS・DHCP・同意画面だけ通す
                                          │         http(80)は同意画面へ誘導
                                          ▼
                                   サーバー 198.51.100.11（同意画面・MySQL）
                                          │ 同意したら：端末のIPを「許可済み」グループへ追加
                                          └──────────▶ core-rt（API／SSH）
```

1. 来場者がQRでWi-Fiにつなぐ。
2. スマホが「ログインが必要」と判断し、同意画面が自動で開く（http通信をVyOSが同意画面へ向けるため）。
3. 同意すると、アプリがcore-rtの許可済みグループにその端末のIPを追加し、インターネットに出られる。
4. 利用期限が来たら、アプリがIPを外す。

予備案：うまく動かないときは「Wi-Fi接続用QRだけで運用」に切り替える（§7）。資料は`当日資料/`（gitに登録しない）。

## 4. 段階2：VyOSで「同意前は止める」を作る（アプリはまだ使わない）

VyOS 1.4の書き方の例。インターフェース名・ルール番号は実際の設定に合わせて確定する。

### ゲストのIP範囲とDHCP（案A、先に切り替える）

| 項目 | 値 |
|---|---|
| VLAN10 | `10.0.0.0/19`（ゲートウェイ10.0.0.1、配る範囲10.0.1.0〜10.0.31.254、約7,900個） |
| VLAN20 | `10.0.32.0/19`（ゲートウェイ10.0.32.1、配る範囲10.0.33.0〜10.0.63.254、約7,900個） |
| リース時間 | 240分（14400秒） |
| 外向き | インターネット側のインターフェースだけで送信元を変換。ゲスト→サーバーは変換しない（§5の接続元アドレスの確認） |

- **リース240分の理由**：端末はリース時間の半分（120分）でリースを更新するため、つながっている端末のリースは常に120分以上残る。同意した時点で、リースは利用期限（120分）より後まで続くので、期限内にそのIPが別の端末に配られることはない。リースの切れ目に合わせて許可を外す仕組みは作らない。
- **範囲の大きさ**：合計約15,800個。1日に来る端末すべてがリースを持ったままでも足りる（3,500人×1.5台でも約5,300台）。範囲が大きいので、返されたばかりのアドレスがすぐ別の端末に配られる可能性も低い（実機で確認）。
- 範囲を広げてもブロードキャストは増えない（増えるのは端末数の分だけ）。AP側の端末間隔離・ブロードキャスト抑制は別に決める。
- 過去資料のゲスト範囲（`202.222.168.0/22`・`202.222.172.0/22`）は使わない。

```text
# ゲスト側のアドレス（今のアドレスを確認してから置き換える）
set interfaces ethernet <ethX> vif 10 address 10.0.0.1/19
set interfaces ethernet <ethX> vif 20 address 10.0.32.1/19

# DHCP（VLAN10。VLAN20は10.0.32.0/19・subnet-id 20で同じ形）
# 要確認：1.4ではsubnet-idが必須か、leaseの単位（秒）をTab補完で確かめる
set service dhcp-server shared-network-name GUEST10 subnet 10.0.0.0/19 subnet-id 10
set service dhcp-server shared-network-name GUEST10 subnet 10.0.0.0/19 option default-router 10.0.0.1
set service dhcp-server shared-network-name GUEST10 subnet 10.0.0.0/19 option name-server <ゲスト用DNS>
set service dhcp-server shared-network-name GUEST10 subnet 10.0.0.0/19 range 0 start 10.0.1.0
set service dhcp-server shared-network-name GUEST10 subnet 10.0.0.0/19 range 0 stop 10.0.31.254
set service dhcp-server shared-network-name GUEST10 subnet 10.0.0.0/19 lease 14400

# インターネット側だけで送信元を変換（既存のsource NATルールとの順番を確認）
set nat source rule <番号> outbound-interface name <外向きIF>
set nat source rule <番号> source address 10.0.0.0/18
set nat source rule <番号> translation address masquerade
```

**確認**：端末に10.0.x.xのアドレスとリース240分が配られ、インターネットに出られる（この時点ではまだ止めていない）。

### 同意前は止める

```text
# 許可済み端末のグループ（最初は空）
set firewall group address-group PORTAL-AUTHED
# ゲストの範囲
set firewall group network-group GUEST-NETS network 10.0.0.0/19
set firewall group network-group GUEST-NETS network 10.0.32.0/19

# ゲスト → サーバー：DNS・DHCP・同意画面(80/443)だけ許可
# ゲスト（許可済み）→ インターネット：許可
# ゲスト（未許可）→ それ以外：拒否
#   ※ 既存ルールとの順番を見てから番号を決める（要確認）

# 未許可端末のhttp(80)を同意画面へ向ける
set nat destination rule 100 inbound-interface name <ゲスト側IF>
set nat destination rule 100 protocol tcp
set nat destination rule 100 destination port 80
set nat destination rule 100 source group network-group GUEST-NETS
set nat destination rule 100 source group address-group '!PORTAL-AUTHED'
set nat destination rule 100 translation address 198.51.100.11
```

- https（443）は誘導しない（証明書エラーになるため）。スマホの「ログインが必要」判定はhttpで行われるので、80番の誘導で足りる。
- 管理画面（`/admin`）にはゲストから届かないようにする（ガイド11章）。

**試験**（端末1台で）：
1. 接続後、インターネットのページが開けない。
2. スマホに「ログインが必要」の表示が出て、同意画面が開く。
3. 手動で`set firewall group address-group PORTAL-AUTHED address <端末のIP>`→commitすると、インターネットに出られる。
4. 同じIPを`delete`すると、再び止まる。

## 5. 段階3：アプリをVyOSと連携させる（アプリ改修）

**実装済み（初期状態は無効）**。`config.json`の`vyos_portal.enabled`を`true`にしたときだけ動く。無効のままなら、今までどおりローカル確認版（同意の保存だけ、通信許可なし）。`production_enabled`・承認状態の`false`は変えていない。

| 改修 | 実装 |
|---|---|
| 入口 | リンクなしで開いた同意画面は、接続元IPが`guest_networks`の範囲なら受け付ける（`POST /v1/contexts`に`launch_ref: null`）。範囲外なら「ゲストWi-Fiの端末として確認できません」。同意を送るときにIPが変わっていたら「画面を開き直してください」 |
| 許可 | 同意を保存すると、約1秒分の同意をまとめて1回のcommitで`PORTAL-AUTHED`へ追加する（1台ずつcommitすると開場直後に追いつかないため）。画面は「準備しています」→「つながりました」と利用期限を表示する |
| 失敗 | core-rtに届かない・拒否されたときは5秒後に再試行し、3回失敗したら画面は「つながっていません」、管理画面に通知`portal_allow_failed`（重大）。端末には同意し直してもらう。応答が来ないまま失敗した場合は、追加が届いていることもあるので、念のためcore-rtから外す操作を入れる（グループにない場合は何もしない） |
| 期限 | 同意から120分。閉場（毎日の提供時間の終わり、17:00）と提供期間の終わりで打ち切る（ガイドC14）。workerが30秒ごとに期限切れを外す。17:00には全員分を1回のcommitで外す |
| 解除の失敗 | 外せるまで30秒ごとに再試行し、3回続いたら通知`portal_revoke_failed`（重大） |
| 同じIP | 同じIPに期限内の別の許可（同意し直し・別のブラウザ）があるあいだは、古い許可が切れても外さない |
| 管理画面 | 「インターネット許可中の端末」「core-rtへの操作の失敗・再試行中」の件数。手動での解除は今までの「受付側で失効させる」ボタン（約1秒でcore-rtからも外れる） |
| CAPPORT | `/capport/api`は、許可中の端末に`captive: false`と残り秒数を返す |
| 安全 | APIキーはデータフォルダーのファイル（設定ファイルには書かない）。core-rtへの接続は証明書を必ず検証する。追加・削除できるのは`guest_networks`の範囲のIPだけで、触るのは`PORTAL-AUTHED`だけ。core-rtを呼ぶあいだはDBのトランザクションを閉じ、MySQLの名前付きロックで同時に1か所だけが変更する |

### 有効にする手順（サーバー担当とVyOS担当）

1. **core-rtのAPIを用意**（VyOS担当）。サーバー（198.51.100.11）からだけ443番で届くようにし、APIキーを作る。キーはチャットやリポジトリに書かず、サーバー担当へ直接渡す。
2. **キーを置く**：データフォルダーに`vyos-api.key`（キー1行だけ）を作り、サービスのアカウントだけが読めるようにする（`chmod 600`）。core-rtの証明書が自己署名なら、その証明書を`vyos-ca.pem`として同じフォルダーに置き、`ca_file`に名前を書く。
3. **DBの権限を付け直す**（今回、`grants`の`authorized_at`・`original_expires_at`、`operations`の`next_attempt`の更新権限が増えた）。`python tools/mysql_grants.py runtime ...`の出力を確認してから、管理者で実行する（ガイド4章）。付け直さないと、同意の後に許可が進まない。
4. **config.json**（アプリとworkerを止めてから書き換える）：
   - `https_transport`：`enabled: true`、`portal_origin`・`admin_origin`・`trusted_proxy: "127.0.0.1"`（ガイド11章）
   - `local_intake_enabled: true`（`vyos_portal`が有効なときだけ、HTTPSと同時に使える）
   - `vyos_portal`：`enabled: true`、`api_origin`（`https://<core-rtのサーバー側アドレス>`。パスなし）、`api_key_file: "vyos-api.key"`、`ca_file`（`null`か`"vyos-ca.pem"`）、`guest_networks: ["10.0.0.0/19", "10.0.32.0/19"]`（ガイドC15）、`access_seconds: 7200`
5. **nginx**：`server/deployment/nginx.portal.conf.template`を写し、`__PORTAL_HOSTNAME__`・`__ADMIN_HOSTNAME__`・`__APP_PORT__`・`__MANAGEMENT_CIDR__`・証明書のパスを書き換えて`nginx -t`。80番は宛先に関係なくhttpsの同意画面へ転送する（OSのログイン確認用）。閉じた状態のひな形（`nginx.closed.conf`）とは同時に使わない。
6. アプリ（serve）とworkerを起動し、`/health/live`の`adapter`が`vyos`になっていることを確かめる。設定に不備があれば起動しない。

### 確認

**試験**：自動試験（VyOSを模したもの）は`server/tests/test_network_access.py`と`tests/portal_network.test.cjs`。次に実機のcore-rtで1台 → 期限切れで止まることを確認（`access_seconds`を一時的に短くしてよい。60秒以上）。

**接続元アドレスの確認**（実機1台目で最初に行う）：同意画面を開いて「ゲストWi-Fiの端末として確認できません」と出たら、アプリに届いた接続元がゲストの範囲外になっている。core-rtがゲスト→サーバーの通信を送信元変換（source NAT／masquerade）しているか、nginxが`X-Forwarded-For`を付けていない。その場合は次の2つが成り立たないので、先へ進まず設定を直す（ゲスト→198.51.100.11は送信元を変換しない）。

- 端末を接続元IPで区別する入口・許可・期限の仕組み（全員が同じ端末に見える）。
- `server/session_guard.py`の発行上限（同じ接続元から1分あたり20件）。全員が1つの接続元になり、1分あたり20件で止まる。上限の値は承認前の暫定値なので、この試験では書き換えない。

### 注意

- 同意の記録（`consents`・`grants`の`connection_ref`）に端末のゲストIP（`ipv4:10.0.x.x`）が残る。削除しない（ガイドC02）。利用条件の文面でIPを記録することに触れるかは運営が決める（要確認）。
- VyOSのAPIはcommitまでで保存（`save`）はしない。core-rtを再起動すると`PORTAL-AUTHED`が空になり、許可中の来場者は同意し直しになる（記録上は期限で切れる）。
- グループから外しても、すでに張られた接続（conntrack）がしばらく残ることがある（§8で要確認）。
- 開場直後に同意が集中したときのcommitの速さは未確認。§6の試験9で台数を増やして確かめる。
- 別のブランチ（`claude/youthful-wing-b3721f`）に、専用の表を2つ追加する別の設計の下書きがある。今回の実装は既存の`grants`・`operations`を使い、表は増やしていない（移行なしで有効にできるため）。その下書きは取り込んでいない。

## 7. 切り戻し（予備案への切り替え）

うまく動かないときは、ゲストを全員許可する状態に戻す。

1. `delete nat destination rule 100`（誘導をやめる）
2. ゲスト→インターネットを、許可済みグループに関係なく許可する（または段階1で保存した設定に戻す）
3. `当日資料/wifi-案内.html`（Wi-Fi接続用QRだけの案内）を掲示する

切り替えの判断者：要確認（停止・再開責任者）。
